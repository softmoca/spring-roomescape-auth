# 06. 공유회 준비 — 같은 요구사항, 다른 선택 비교하기

> 이 문서는 **7번 대화**에서 채워진다.
> 자세한 설명은 각 단계 docs(02~05)에 있다. 이 문서는 공유회 자리에서 빠르게 비교하기 위한 **요약본**.

## 공유회의 목적

구현 결과 발표가 아니다. 같은 요구사항을 해결하면서 각자가 어떤 선택을 했는지 비교하는 시간이다.

---

## 내 선택 요약 (5개 비교 지점)

### 1. 로그인 상태 유지 방식

- **선택:** 웹은 `HttpSession`, 모바일은 JWT (공존)
- **다른 후보:** 세션 단일 / 토큰 단일 / OAuth
- **선택 이유:** 미션이 "웹 → 모바일 확장"으로 설계되어 있어, 공존을 통해 두 방식의 트레이드오프를 직접 비교하려고 의도적으로 분리. 통일하면 비교 학습 기회가 사라짐.
- **받아들인 트레이드오프:** 동시 로그인 방지 같은 통합 운영 요구가 오면 "왜 분리했는가"가 흐려짐 (4단계에서 실제로 만남).

→ 자세히: `02-step1-web-auth.md` §3.1, `03-step2-mobile-auth.md` §3.1

---

### 2. 인증 공통 처리 위치

- **선택:** Interceptor + ArgumentResolver **조합**
    - `LoginCheckInterceptor` — 1차 차단 (`@LoginMember` 파라미터 존재로 인증 필요 판단)
    - `LoginMemberArgumentResolver` — 2차 안전망 + `Member` 객체 주입
- **다른 후보:** Interceptor 단독 / ArgumentResolver 단독 / Filter
- **선택 이유:** 둘의 역할이 다르다 — "통과시킬까?"(Interceptor)와 "누구의 요청인지 알려줘"(ArgumentResolver). 어느 한쪽만 쓰면 다른 역할을 컨트롤러가 다시 해야 함.
- **받아들인 트레이드오프:** 세션 검사 코드가 두 곳에 존재(2단계에서 `AuthenticationExtractor`로 위임시켜 해소).

→ 자세히: `02-step1-web-auth.md` §3.3

---

### 3. 모바일 앱 요청 인증 방식

- **선택:** `Authorization: Bearer <JWT>` 헤더 + `/api/login` 별도 엔드포인트
- **공통 구조:** `AuthenticationExtractor` 인터페이스 + `SessionAuthenticationExtractor` / `TokenAuthenticationExtractor` 구현체. Interceptor·ArgumentResolver는 추출기에 위임만.
- **다른 후보:** 웹·모바일 통합 엔드포인트(`/login`에서 분기) / 쿠키를 모바일에서도 사용 / if-else 분기
- **선택 이유:** "바뀌는 건 추출기 한 층뿐"이라는 추상화의 가치 — 새 인증 방식이 늘어도 구현체 하나만 추가하면 됨. 엔드포인트도 응답 형태가 달라(쿠키 vs 토큰) 분리하는 게 응집도상 자연스러움.
- **불편했던 점:** 토큰 즉시 무효화 불가능. 만료도 의도적으로 단순화 — 청구서가 4단계에서 옴.

→ 자세히: `03-step2-mobile-auth.md` §3.1, §3.3

---

### 4. 인가 판단 위치

- **선택:** Service 주 방어선(B) + Domain 메서드 위임(C) + Interceptor 거친 체(E)의 **3층 조합**
    - `ManagerCheckInterceptor` — "매니저인가?" (요청 정보만으로 판단 가능)
    - `ReservationService` — "자기 매장 예약인가?" (예약을 조회한 뒤에야 판단 가능)
    - `manager.canManage(reservation)` — Service가 도메인 메서드에 위임 (인가 의도를 코드 언어로 표현)
- **다른 후보:** Controller 단독 / Repository 쿼리 조건 / `AccessPolicy` 객체
- **선택 이유:** **판단에 필요한 정보가 모이는 가장 이른 지점에서 처리.** 역할은 요청 시점에 알 수 있고, 매장 비교는 데이터를 손에 쥔 후에야 가능. 둘이 자연스럽게 두 층으로 나뉨.
- **받아들인 트레이드오프:** Interceptor와 Service에서 Manager 조회가 중복(`/admin/**` 요청당 DB 2회). 토큰 클레임에 임베드하면 stale 위험 + 4단계 무효화와 묶임.

→ 자세히: `04-step3-authorization.md` §3.1

---

### 5. 실패 응답 설계 (401 / 403 / 404)

- **선택:** **영역별로 다른 코드**
    - 비로그인 → **401** (모든 영역)
    - 일반 사용자가 타인 예약 접근 → **404** (예약 존재 자체를 숨김)
    - 매니저가 타 매장 예약 접근 → **403** (내부 운영자에게 명확한 피드백)
- **다른 후보:** 403 통일 / 404 통일
- **선택 이유:** 응답을 받는 사람이 다르면 적절한 정보량도 다르다. 일반 사용자에겐 다른 예약의 존재를 노출할 이유가 없고, 매니저에겐 "다른 매장이라 못 한다"는 명시적 피드백이 의미가 있음.
- **받아들인 트레이드오프:** 403/404를 영역별로 다르게 매핑하는 로직이 Service에 생김. 통일하면 코드는 단순하지만 사용자별 피드백이 어색해짐.

→ 자세히: `04-step3-authorization.md` §3.4

## 가장 이야기하고 싶은 선택 지점 (1개)

```
나는 "웹은 세션 + 모바일은 JWT 공존"을 선택했다.
다른 후보는 "토큰 단일로 통일"이었다.
이 방식을 선택한 이유는 두 방식의 트레이드오프를 직접 비교하기 위해서였고,
그 비교가 4단계 동시 로그인 방지에서 가장 선명하게 드러났다 —
세션은 "역방향 인덱스 부재"라는 운영 문제로 환원되지만,
토큰은 "stateless 전제 자체가 깨진다"는 본질적 충돌과 만난다.
이 비대칭이 인증 방식 선택의 진짜 비용이었다.
```

## 다른 사람에게 묻고 싶은 점

- **토큰 단일로 간 사람:** 동시 로그인 방지를 어떤 방식으로 풀었나? 화이트리스트 / 블랙리스트 / `token_version` / Refresh Token 중 어느 쪽? stateless 전제가 깨진다는 사실을 어떻게 받아들였나?
- **세션 단일로 간 사람:** 모바일에서 쿠키를 어떻게 다뤘나? 어색함을 무엇으로 갚았나?
- **인가 판단을 Domain에 더 둔 사람:** Service에서 데이터를 손에 쥐기 전에 어떻게 도메인 객체로 판단을 옮겼나? `AccessPolicy` 같은 객체를 별도로 뒀나?
- **403/404를 통일한 사람:** 영역별로 다른 피드백이 필요하다고 느낀 순간이 있었나? 아니면 통일이 더 깔끔하다고 끝까지 느꼈나?
- **인증 공통 처리를 Filter로 한 사람:** Interceptor 대비 무엇이 더 좋았나? 예외 처리(`GlobalExceptionHandler`로 연결)는 어떻게 풀었나?

## 최종 PR 본문 (전체)

```
1단계 - 웹 로그인
- 로그인 상태 유지 방식: HttpSession + 쿠키 (서버 메모리에 LOGIN_MEMBER_ID 저장)
- 인증이 필요한 API: @LoginMember 파라미터 존재로 선언 (어노테이션 기반)
- 공통 처리 위치: LoginCheckInterceptor(1차 차단) + LoginMemberArgumentResolver(주입) 조합
- 테스트한 인증 실패 상황: 비로그인 401, 잘못된 비밀번호 401, 존재하지 않는 이메일 401,
  로그아웃 후 접근 401, 이메일 누락 400

2단계 - 모바일 앱 요청 인증
- 선택 도구: 웹은 HttpSession(쿠키), 모바일은 JWT(Authorization: Bearer 헤더).
  AuthenticationExtractor 인터페이스 + Session/Token 두 구현체로 통합.
  /api/login 별도 엔드포인트.
- 다른 후보: 세션 단일로 모바일까지 / 토큰 단일로 통일 /
  Interceptor·ArgumentResolver에 if-else 분기
- 선택 이유: 두 방식의 트레이드오프를 비교하기 위해 공존 유지.
  "바뀌는 건 추출기 한 층뿐" 추상화로 Interceptor·Resolver·Controller 무수정.
- 불편하거나 아쉬운 점: 토큰 즉시 무효화 불가, 만료 단순화 — 4단계에서 청구서가 옴.

3단계 - 인가
- 선택 도구:
  - 인가 판단: Service 주 방어선(B) + Domain 메서드 위임(C) + Interceptor 거친 체(E) 조합
  - 매니저-매장 관계: Manager 별도 도메인, 1:1 시작
  - 예약-매장 연결: Theme.storeId 경유
  - 인가 실패 응답: 영역별 분리 — 사용자=404, 매니저=403
- 다른 후보: Controller 단독 인가 / Member.role + Member.storeId / 403 통일 / 404 통일
- 선택 이유: 판단에 필요한 정보가 모이는 가장 이른 지점(Service)에서 처리.
  manager.canManage(reservation)으로 도메인 언어가 코드에 그대로 드러남.
  응답을 받는 사람에 따라 적절한 정보량이 다르므로 영역별 코드 분리.
- 인가 판단 위치:
  - ManagerCheckInterceptor: "매니저인가?" 거친 체 → 비로그인 401, 매니저 아님 403
  - ReservationService: "자기 매장 예약인가?" 고운 체 → 타 매장 403, 없는 예약 404
- 유지하거나 변경하고 싶은 점:
  - 유지: Service 인가 + Domain 메서드 위임 조합
  - 변경 고려: Manager 조회 이중 발생 → 4단계 토큰 무효화 해결 후 클레임 임베드 검토

4단계 - 동시 로그인 방지 (자율, 설계만)
- 시도한 방식: 코드 구현 없음. 슬롯별 후보 비교 + 미래 구현 스케치만.
- 막힌 지점: 세션은 "역방향 인덱스 부재"라는 운영 문제로 환원.
  토큰은 "JWT는 자기완결적이라 외부 상태 없이는 무효화 불가" — 본질적 충돌.
  공존 운영은 통합하면 분리한 이유가 흐려지는 모순.
- 알게 된 점: JWT의 stateless = "운영 요구사항이 없을 때만 stateless".
  "stateless"는 이진이 아니라 self-contained payload + stateful invalidation의 스펙트럼.
- 다시 한다면 바꾸고 싶은 점: 충돌 정책 미정 결정은 유지(어느 정책이든 핵심 비대칭은 같음).
  2단계에서 jti와 만료를 미리 넣어뒀으면 4단계 결의가 작아졌을 것.
```
