# 07. 개선 작업장 인덱스

> 미션 종료 후 이 레포의 개선 활동을 모아두는 살아 있는 인덱스.
미션 기간 사료(00 ~ 06, decisions/ 일부)는 frozen.
이 문서는 카탈로그일 뿐, 실제 작업은 08~ 새 파일과 decisions/에서 진행된다.
>

---

## 1. 이 문서의 역할

00이 "미션의 지도"라면, 이 문서는 "미션 종료 후의 개선 작업장 인덱스"다.
미션 기간(2026-05-22 종료)의 학습 기록은 02~06과 decisions/에 frozen 상태로 남아 있고,
이후 이 레포에서 일어나는 모든 작업의 시작점이 이 문서다.

- **개선 후보 카탈로그** — 작업 대상이 될 수 있는 항목들의 목록. 우선순위·종류 표시.
- **작업 추적** — 각 항목의 상태 (미착수 / 진행 중 / 완료 / 설계만 / 보류).
- **개별 작업 기록은 여기 적지 않는다.** 작업이 시작되면 08, 09... 새 파일을 만들고, 이 문서는 거기로 가리키기만 한다.
- **결정으로 박힌 것은 decisions/에 별도 ADR**이 되고, 이 문서가 그 ADR을 가리킨다.

이 문서는 자주 갱신된다. 미션 기간의 사료적 문서들과 성격이 다르다는 점에 주의.

## 2. 첫 후보들의 출처

이 인덱스의 초기 항목들(I-1 ~ I-13)은 미션 기간 문서의 다음 자리에서 추출했다.

- `02-step1-web-auth.md` 의 "9. 다음 단계 (모바일 인증)로 넘기는 질문" 5개
- `03-step2-mobile-auth.md` 의 "9. 다음 단계 (인가)로 넘기는 질문" 3개
- `04-step3-authorization.md` 의 "9. 다음 단계 (동시 로그인 방지)로 넘기는 질문" 5개
- `05-step4-concurrent-login.md` 의 "9. 다시 한다면 바꾸고 싶은 점" 6개 + "12. 다음 단계 (공유회)로 넘기는 질문" 5개

총 24개 원시 항목을 정리해 중복을 합치고, 단순 회고(코드 변경 의도가 없는 관조)는 제외했다. 결과가 아래의 13개.

이후 새 항목이 추가될 때는 다음 형식으로 출처를 같이 적는다.

- "구현 중 발견" — 08~ 작업 도중 새로 떠오른 후보
- "외부 영감" — 다른 사람 코드, 글, 공유회 발표에서 영감 받은 후보
- "재검토 결과" — 이미 완료된 항목을 다시 봤더니 추가 작업이 보임

### 갈래 A: 인증 인프라

**I-1. ArgumentResolver의 매 요청 DB 조회 비용 완화**

- **출처:** 02 §9-2
- **종류:** ADR?
- **우선순위:** 중
- **예상 작업량:** 후보 비교만 0.5일 / 실제 도입까지 1~2일
- **핵심 질문:** 인증된 모든 요청마다 `MemberService.findById()` 1회가 발생한다. 후보는 (1) 세션에 Member 객체 캐싱, (2) 토큰 claim에 필요 정보 임베드 (I-4와 합류), (3) 그냥 둠 (현재 규모에서 무시 가능). 어느 게 맞는가, 아니면 셋이 다 답이고 트래픽 임계만 다른가.
- **묶임:** I-3 (Manager 조회 이중화)와 자료구조가 비슷. I-4 (claim 임베드)와는 후보 (2)가 직접 겹침. 셋을 같이 풀면 한 ADR로 묶일 수도 있음.
- **상태:** 미착수

**I-2. `@LoginMember` Fail-open 보완 (`@LoginRequired` 도입 검토)**

- **출처:** 02 §3.2 트레이드오프 + 02 §3.4 다시 결정할 조건
- **종류:** exec
- **우선순위:** 하
- **예상 작업량:** 0.5일
- **핵심 질문:** 현재 "`@LoginMember` 파라미터 존재 = 인증 필요"라는 규칙 때문에, 응답에 사용자 정보가 필요 없는 인증 API가 생기면 어노테이션을 빠뜨려 뚫린다. `@LoginRequired` 별도 어노테이션을 추가할지, 추가한다면 `@LoginMember`와의 책임 경계를 어떻게 정할지.
- **묶임:** I-13 (`/admin/**` 책임 경계 명시화)와 함께 보면 인증 진입 규칙 전체가 한 자리에 정리됨.
- **상태:** 미착수

**I-13. `/admin/**`의 LoginCheckInterceptor·ManagerCheckInterceptor 책임 경계 명시화**

- **출처:** 02 §9-3
- **종류:** exec (작은 ADR로 박힐 가능성 있음)
- **우선순위:** 하
- **예상 작업량:** 0.5일
- **핵심 질문:** 현재 LoginCheckInterceptor가 `/admin/**`을 excludePathPatterns로 빼고, ManagerCheckInterceptor가 `/admin/**`에서 로그인+매니저를 함께 본다. 이 책임 분담이 의도된 것인데, 다른 사람이 코드를 봤을 때 "왜 /admin은 LoginCheck를 거치지 않는가"가 헷갈릴 수 있음. 주석으로 둘지, ManagerCheckInterceptor가 LoginCheck를 내부적으로 호출하는 구조로 합칠지, 그대로 둘지.
- **묶임:** I-2와 함께 인증 진입 규칙 일괄 정리.
- **상태:** 미착수

### 갈래 B: 인가 흐름

**I-3. Manager 조회의 Interceptor·Service 이중 발생 해소**

- **출처:** 04 §9-1, 04 §7-6 (인사이트), 04 §8.5 Q5
- **종류:** ADR
- **우선순위:** 중
- **예상 작업량:** 후보 비교 0.5일 / 실제 도입 1~2일
- **핵심 질문:** ManagerCheckInterceptor가 `findByMemberId()`로 매니저인지 확인하고, ReservationService가 다시 `findByMemberId()`로 매니저를 꺼낸다. `/admin/**` 요청 1건당 Manager DB 조회가 2회. 후보는 (1) request attribute로 Interceptor에서 Service로 Manager 전달, (2) 세션에 Manager 캐싱 (I-5의 stale 문제와 만남), (3) JWT claim에 storeId 임베드 (I-4로 합류). 각 후보가 책임 경계를 어떻게 바꾸는가.
- **묶임:** I-4, I-5와 같은 자료구조 문제. 셋을 같이 푸는 게 자연스러움. I-1 (ArgumentResolver DB 조회)과도 패턴이 동일.
- **상태:** 미착수

**I-4. JWT claim에 `storeId`·role 임베드 + 매장 변경 시 재발급**

- **출처:** 03 §9-1, 03 §9-2, 04 §9-3
- **종류:** ADR
- **우선순위:** 중
- **예상 작업량:** 후보 비교 1일 / 실제 도입 2~3일 (재발급 흐름까지)
- **핵심 질문:** 토큰 페이로드에 현재 `memberId`만 있다. `storeId`나 role을 넣으면 매 요청 DB 조회가 사라지지만, 매니저가 매장을 바꾸면 기존 토큰이 stale이 된다. 후보는 (1) 넣지 않고 매 요청 DB 조회 (현재), (2) 넣고 매장 변경 시 강제 재발급, (3) 넣되 만료를 짧게 + Refresh로 자연스럽게 갱신. 토큰 무효화(I-8)와 본질적으로 같은 문제.
- **묶임:** I-3, I-5, I-8과 한 묶음. 사실상 이 네 항목을 동시에 풀어야 답이 일관됨.
- **상태:** 미착수

**I-5. 세션 캐싱 시 매니저 매장 변경의 stale 데이터 무효화 전략**

- **출처:** 04 §9-2
- **종류:** ADR?
- **우선순위:** 하
- **예상 작업량:** I-3을 진행하면서 같이 풀림. 단독 0.5일
- **핵심 질문:** I-3의 후보 (2)(세션에 Manager 캐싱)를 채택할 때만 등장하는 하위 문제. 매니저의 매장이 바뀌었을 때 세션 캐시를 어떻게 무효화하는가. 후보는 (1) TTL 기반 (짧으면 결국 매 요청 조회와 같음), (2) 매장 변경 API에서 해당 매니저의 세션 캐시 명시적 invalidate, (3) 세션 캐싱 자체를 포기하고 다른 후보로 감.
- **묶임:** I-3에 종속. I-3에서 (2)를 안 고르면 I-5는 자동으로 의미 없어짐.
- **상태:** 미착수

**I-12. 인가 실패 응답을 웹/모바일에 동일하게 둘지**

- **출처:** 03 §9-3
- **종류:** exec
- **우선순위:** 하
- **예상 작업량:** 0.5일
- **핵심 질문:** 03 §9-3에서 "모바일에서도 403을 동일하게 처리할 것인가, 응답 형태를 다르게 할 필요가 있는가"를 미결로 남겼다. 현재 GlobalExceptionHandler가 두 클라이언트를 구분하지 않고 같은 형식으로 응답한다. 이를 의도된 결정으로 박을지(현재 상태 유지), 아니면 모바일에 특화된 응답 형태를 추가할지. 검토 결과 "유지"로 끝날 가능성이 높지만, 그 결정을 명시적으로 남기는 의미가 있음.
- **묶임:** 없음.
- **상태:** 미착수

### 갈래 C: 운영·보안

**I-6. 비밀번호 평문 저장 → BCrypt 해시**

- **출처:** 02 §9-4
- **종류:** exec
- **우선순위:** 중
- **예상 작업량:** 1일 (해싱 도입 + 기존 data.sql 갱신 + 로그인 흐름 점검 + 테스트 수정)
- **핵심 질문:** 미션 기간 의도적 단순화로 평문이었던 비밀번호를 BCrypt 등으로 해시. 핵심 결정 갈림은 거의 없음 (BCrypt가 사실상 표준). 다만 (1) Member 도메인의 책임을 어디까지 둘지 (해시는 누가? 도메인 / 서비스 / 별도 PasswordEncoder), (2) data.sql의 시드 비밀번호를 어떻게 처리할지가 작은 결정.
- **묶임:** 없음. 다른 갈래와 독립.
- **상태:** 미착수

### 갈래 D: 운영 요구 (동시 로그인 방지)

> 05의 설계 스케치(§4.5)가 이미 충분히 자세하다. 이 갈래의 항목들은 그 설계를 코드로 구현하는 단계.
>

**I-7. 동시 로그인 방지 — 세션 쪽 실제 구현**

- **출처:** 04 §9-4, 05 §4.5.1 (구현 스케치), 05 §12-1
- **종류:** ADR
- **우선순위:** 중
- **예상 작업량:** 2~3일 (충돌 정책 결정 + ActiveSessionRegistry 구현 + HttpSessionListener 연결 + 테스트)
- **핵심 질문:** 05에서 충돌 정책을 의도적으로 미정으로 두고 잠정 설계(B = 새 로그인 우선)만 했다. 실제 구현 시 (1) 충돌 정책 확정, (2) ActiveSessionRegistry의 인메모리/JDBC 중 선택, (3) HttpSessionListener로 만료 동기화. 05 §4.5.1의 스케치를 출발점으로.
- **묶임:** I-8과 한 묶음으로 풀어야 공존 운영 결정(I-9)이 의미 있어짐.
- **상태:** 미착수

**I-8. 동시 로그인 방지 — 토큰 쪽 실제 구현 (token_version 또는 화이트리스트)**

- **출처:** 04 §9-3, 04 §9-4, 05 §4.5.2 (구현 스케치), 05 §7-9 (token_version 인사이트), 05 §12-2
- **종류:** ADR
- **우선순위:** 중
- **예상 작업량:** 2~3일 (자료구조 선택 + JWT 흐름 수정 + 만료 도입 + 테스트). I-7과 같이 하면 +0.5일 정도
- **핵심 질문:** 05에서 잠정 설계만 한 두 변형 — (1) active_token 화이트리스트 (jti + expires_at), (2) Member.token_version 단일 정수 컬럼 — 중 어느 쪽으로 갈지. 그 선택이 I-4(claim 임베드)와 어떻게 묶이는지. 2단계에서 만료(`exp`)를 빼둔 결정이 여기서 청구서로 돌아옴 — 만료를 같이 도입해야 GC가 자연스러움.
- **묶임:** I-4 (claim 구조 변경)와 사실상 한 작업. I-7과 함께 풀어야 I-9가 의미 있음.
- **상태:** 미착수

**I-9. 공존 운영에서 통합 vs 분리 관리**

- **출처:** 05 §4.1, 05 §9 (다시 한다면), 05 §12-3
- **종류:** ADR
- **우선순위:** 하
- **예상 작업량:** I-7, I-8을 끝낸 후에 결정. 단독 1일 (설계 비교만)
- **핵심 질문:** 웹(세션)과 모바일(JWT)이 공존하는 현재, 동시 로그인 방지를 (A) 회원 단위로 통합해서 `active_auth` 한 테이블로 관리할지, (B) 세션과 토큰을 각각 별도로 관리할지. 통합하면 정책은 깔끔하지만 2단계에서 의도적으로 분리한 학습 이유가 운영 레이어에서 사라진다는 모순이 있음. 05에서 잠정 B로 두고 미결로 남김.
- **묶임:** I-7, I-8 이후에만 의미가 있음. 둘 다 끝나야 비교할 대상이 생김.
- **상태:** 미착수

**I-10. 강제 로그아웃 응답 코드 분리 (401 + code 필드)**

- **출처:** 05 §4.2, 05 §12-4
- **종류:** exec
- **우선순위:** 하
- **예상 작업량:** 0.5일
- **핵심 질문:** 동시 로그인 방지 정책 B(새 로그인 우선) 채택 시, 첫 기기는 다음 요청에서 401을 받는다. 그게 일반 만료인지 강제 로그아웃인지 클라이언트가 구분 못한다. 05 §4.2에서 잠정 결정한 "401 + `{"code": "SESSION_TERMINATED", "message": "..."}` 형식의 ForcedLogoutException 도입"을 실제로 구현. 결정은 거의 박혀 있어 실행 위주.
- **묶임:** I-7 또는 I-8을 진행할 때 자연스럽게 끼워서 함.
- **상태:** 미착수

**I-11. 매니저-매장 1:1 → 1:N 확장 (매핑 테이블 도입)**

- **출처:** 04 §3.2 (잠정 1:1 시작), 04 §4.2 (발전 경로 스케치), 04 §8.5 Q4
- **종류:** ADR
- **우선순위:** 하
- **예상 작업량:** 1~2일 (스키마 변경 + Repository 메서드 시그니처 변경 + Service 인가 로직 수정 + 테스트)
- **핵심 질문:** 현재 `manager(id, member_id, store_id)`의 1:1 구조를 `manager(id, member_id)` + `manager_store(manager_id, store_id)` 매핑 테이블로 전환. 04 §4.2의 발전 경로가 이미 자세히 그려져 있어, 결정 자체는 거의 박혀 있음. 다만 (1) 언제 전환할지 (요구사항이 들어왔을 때 vs 미리), (2) `ManagerRepository.findStoreIdsByMemberId()` 반환 타입을 List로 할지 Set으로 할지 같은 작은 결정은 남음.
- **묶임:** 없음. 다른 갈래와 독립.
- **상태:** 미착수

## 4. 한 활동이 끝났을 때 어떻게 기록하는가

세 가지 패턴이 있다.

**경우 A — 코드 변경 + 결정 박힘**

- `08-<주제>.md` 작업 기록 + `decisions/00X-<주제>.md` ADR 같이 작성
- 이 문서(07)의 해당 항목 상태: `미착수` → `완료 (08-<주제>, ADR-00X)`

**경우 B — 코드 변경만 (결정 없이)**

- `08-<주제>.md` 만 작성, ADR 없음
- 상태: `완료 (08-<주제>)`
- 코드 디프와 작업 기록만으로 자기설명되는 변경에 적용

**경우 C — 설계만, 코드 없음 (05단계처럼)**

- `08-<주제>.md` 에 설계만 기록
- 상태: `설계 완료 (08-<주제>) / 구현 보류`

미션 기간의 02~05 + decisions/ 흐름을 그대로 이어받는 모양이다.

## 5. 새 파일 명명 규칙

### 작업 기록

- 형식: `NN-<짧은-주제>.md` (예: `08-arg-resolver-caching.md`)
- 번호: 시작순. 미션 기간(02~06)을 이어받아 08부터.
- 주제명: kebab-case, 영문 권장. 한 작업이 한 파일.

### ADR

- 형식: `decisions/NNN-<주제>.md` (예: `decisions/007-arg-resolver-db-caching.md`)
- 번호: 미션 기간의 ADR(001~)을 이어받아 다음 번호부터.
- 미션 기간 ADR이 별도 대화에서 001~006으로 박힐 예정이므로, 미션 후 첫 ADR은 007이 됨.

### 연결 (cross-link)

- 한 작업 기록 파일이 여러 ADR을 만들 수 있다. 그 경우 작업 기록 본문 끝에 ADR 목록을 적는다.
- 한 ADR이 여러 작업 기록을 가리킬 수도 있다. ADR 본문에 "관련 작업 기록" 절을 둔다.
- 이 인덱스(07)는 항상 두 가지 모두에 링크한다 — 작업 기록과 ADR을 함께.
