# 05. 4단계 — 동시 로그인 방지 (자율)

> 이 단계의 핵심 질문: **stateless한 인증 구조가 운영 요구사항과 충돌하면 어떻게 풀 것인가?**
>
> **완성이 아니라 "막힌 지점 이해"가 목표.**
>
> 이 문서는 **6번 대화 (Sonnet)** 에서 채워진다.
> **이번 단계는 코드 구현 없이 설계만 수행했다.** 미래에 시간이 생겼을 때 이 문서를 출발점으로 세션·토큰 양쪽의 구현을 다시 그릴 수 있도록 깊이 있게 정리한다.

---

## 1. 요구사항 요약 (가이드 발췌)

### 목표

- 동시 로그인 방지 요구사항이 인증 방식과 어떻게 연결되는지 이해한다.
- 세션 방식에서 동시 로그인을 제한하는 방법을 검토한다.
- 토큰 방식에서 이미 발급된 토큰을 무효화하는 어려움을 경험한다.
- stateless한 구조가 운영 요구사항과 충돌할 수 있음을 이해한다.

### 요구사항

- 같은 계정으로 여러 기기에서 동시에 로그인하는 상황을 제한한다.
- 새 로그인이 발생했을 때 기존 로그인 상태를 어떻게 처리할지 정한다.
- 기존 로그인을 유지할지, 새 로그인을 우선할지 정책을 정한다.
- 세션 또는 토큰 방식에서 이 요구사항을 구현할 때 어떤 어려움이 있는지 정리한다.

### 구현 조건

- 어떤 지점에서 어려웠는지 설명하면 된다. (코드 완성 강제 아님)
- 현재 미션에서 선택한 인증 방식을 기준으로 먼저 검토한다.

### 완료 기준

- [x]  동시 로그인 방지 요구사항을 현재 인증 방식에서 검토했다.
- [x]  구현하거나 설계한 방식을 설명했다.
- [x]  막힌 지점과 알게 된 점을 정리했다.
- [x]  토큰의 stateless한 특성이 깨질 수 있는 지점을 인식했다.

## 2. 내가 선택한 인증 방식에서의 출발 상태

> 3단계까지 완료된 시점의 실제 상태. 4단계 시작 전 현황 파악용.

### 현재 인증·인가 구조 요약

**웹 (세션):**

- `POST /login` → `HttpSession`에 `LOGIN_MEMBER_ID: memberId` 저장 → `JSESSIONID` 쿠키 발급
- 매 요청마다 `SessionAuthenticationExtractor`가 세션에서 `memberId` 추출
- 로그아웃: `POST /logout` → `session.invalidate()` → 세션 파기

**모바일 (JWT):**

- `POST /api/login` → HS256 서명 JWT 발급 → `Authorization: Bearer {token}` 헤더로 전달
- 매 요청마다 `TokenAuthenticationExtractor`가 헤더에서 토큰 파싱 → `memberId` 추출
- 토큰 무효화: **현재 없음** — 2단계에서 best-effort로 단순화, 4단계로 이월

**공통 추출 구조:** `AuthenticationExtractor` 인터페이스 + 두 구현체. `LoginCheckInterceptor`와 `LoginMemberArgumentResolver`는 추출기 목록에 위임만 한다.

**인가 (3단계 추가):**

- `ManagerCheckInterceptor`: `/admin/**` 진입 시 `findByMemberId(memberId)` → 매니저 아니면 403
- `ReservationService.deleteByManager()`: 예약 조회 후 `manager.canManage(reservation)` → 타 매장이면 403

---

### 동시 로그인 방지 관점에서의 현재 상태

**세션 방식에서 서버가 "누가 로그인 중인지" 알고 있는가?**

절반만 안다. `HttpSession`은 서버 메모리(또는 세션 스토어)에 살아있으므로 원칙상 "지금 살아있는 세션 목록"을 조회할 수 있다. 그러나 현재 구현에는 `memberId → sessionId` 매핑이 없다. 세션에는 `sessionId → memberId` 방향만 있어서, 특정 회원의 기존 세션을 찾아 무효화하는 것이 바로 가능하지 않다.

**토큰 방식에서 서버가 "누가 로그인 중인지" 알고 있는가?**

전혀 모른다. JWT는 발급하면 끝이다. 서버는 어떤 토큰이 현재 유효한지 추적하지 않는다. 토큰 자체가 유효 기간 내에 있으면 서버는 무조건 믿는다. 기존 토큰을 무효화할 방법이 현재 구조에 없다.

**미리 추측하는 막힐 지점:**

- **세션이라면:** 새 로그인 시 `memberId`로 기존 세션을 찾아야 하는데, 현재 `LoginCheckInterceptor`는 `sessionId → memberId` 방향만 알고 있다. `memberId → sessionId` 역방향 조회를 위한 별도 저장소(Map, DB, Redis)가 필요하다. 서버가 여러 대이면 인메모리 Map으로는 불가능하다.
- **토큰이라면:** 이미 발급된 토큰을 무효화하려면 서버가 "어떤 토큰이 유효한지"를 추적해야 한다. 블랙리스트 또는 `active_token` 테이블 방식 모두 매 요청마다 DB 조회가 필요하다. 이 순간 JWT의 stateless 특성이 깨진다. "stateless이기 때문에 JWT를 쓴다"는 전제가 흔들린다.
- **두 방식 공존 (현재 상태):** 웹(세션)과 모바일(JWT)이 동시에 운영 중이다. 같은 계정으로 웹 세션 1개 + 모바일 토큰 N개가 동시에 존재할 수 있다. 동시 로그인 방지 정책을 세션과 토큰에 각각 다르게 적용해야 하는가, 아니면 회원 단위로 통합해서 관리해야 하는가? 이 질문이 4단계의 핵심 어려움이 될 것 같다.
- **3단계 인가와의 연결:** `ManagerCheckInterceptor`는 매 요청마다 `managerRepository.findByMemberId()`를 호출한다. 동시 로그인 방지를 위해 `active_session` DB 조회까지 추가되면 `/admin/**` 요청 1건당 DB 조회가 최소 3회(Manager 조회 × 2 + 세션 유효성 조회)가 된다. 이 비용이 허용 가능한가를 4단계에서 고민해야 한다.

## 3. 가이드가 명시한 선택 카테고리

### 3.1 충돌 정책

**가이드 질문:** 기존 로그인을 유지할 것인가, 새 로그인을 우선할 것인가?

| 후보 | 동작 | 장점 | 단점 | 내 선택 |
| --- | --- | --- | --- | --- |
| A. 기존 로그인 유지, 새 로그인 거부 | 두 번째 기기에 401 + "다른 기기에서 로그인 중" 메시지 | 사용자 의도(현재 기기 보호) 명확. 탈취된 토큰이 추가 로그인 못 함 | UX 매우 불편 — 첫 기기 잃거나 로그아웃 못 하면 영영 못 들어옴. 강제 로그아웃 별도 API 필요 | — |
| B. 새 로그인 우선, 기존 무효화 | 두 번째 기기 성공 → 첫 기기 다음 요청부터 401 | 일반적 UX. "새 기기 들어오면 이전 끊긴다"가 익숙 | 첫 기기 갑자기 끊김. **탈취된 토큰이 로그인하면 정상 사용자가 쫓겨남**(B의 숨은 함정) | — |
| C. 둘 다 허용 (현재 상태) | 변경 없음 | 단순 | 요구사항 자체를 안 푼 것 | — |

**선택:** **미정.** 표만 채우고 정하지 않고 둔다.

**선택하지 못한 이유:** 4단계 학습 목표를 정직하게 따른 결과다. 가이드가 명시한 학습 목표는 "동시 로그인 방지가 인증 방식과 어떻게 연결되는지 이해"인데, **충돌 정책 자체는 인증 방식과 무관하게 운영 정책의 영역**이다. 같은 정책 A를 세션 위에서 구현하기와 토큰 위에서 구현하기는 완전히 다른 그림이 되고, 어려움도 거기서 나온다. 정책을 한쪽으로 가정해버리면 "이 정책이라서 세션은 되는데 토큰은 안 된다"는 식의 잘못된 결론으로 흐를 위험이 있다. 정책 A든 B든, 어느 쪽을 골라도 **세션에서는 "메커니즘이 있다(만든다)"가 되고 토큰에서는 "메커니즘이 없다(만들어야 한다)"가 된다.** 이 비대칭이 4단계의 본체다.

**다시 결정할 조건:** 실제 운영팀에서 사용자의 동시 로그인 패턴 데이터(같은 계정 다중 기기 사용 빈도, 강제 무효화에 대한 불만 빈도)가 있을 때. 그 전엔 어느 쪽도 추측에 가깝다.

### 3.2 상태 저장 위치

| 후보 | 동작 | 장점 | 단점 | 내 선택 |
| --- | --- | --- | --- | --- |
| A. 인메모리 (`Map<MemberId, SessionId/TokenId>`) | 서버 메모리에 직접 보관 | 단순, 빠름, 외부 인프라 0 | **서버 재시작 시 모든 로그인 무효화. 다중 서버에서는 서버마다 다른 상태**(동기화 불가). 학습용 외에는 부적합 | — |
| B. DB 테이블 (`active_session`) | 영속, 모든 서버가 같은 상태 공유 | 다중 서버 가능. 영속. 별도 인프라 추가 0(기존 H2/RDB 재사용) | 매 요청마다 SELECT — 인증된 요청 전체의 DB 부담 증가. 3단계 인가의 Manager 조회와 누적되면 `/admin/**` 요청당 DB 3회 | 잠정 |
| C. 별도 캐시 (Redis 등) | TTL·키 만료 같은 캐시 의미가 잘 맞음 | 빠른 조회. 세션·토큰 무효화에 자연스럽게 어울리는 자료구조 | 외부 인프라 추가. 미션 범위 초과 | — |

**잠정 선택:** **B (DB 테이블)** — 단, 4단계에서 실제로 구현하지는 않음. 설계로만 멈춤.

**잠정 선택 이유:**
- 미션 환경에서 외부 인프라(C)는 과하고, 인메모리(A)는 다중 서버 가정에서 의미가 없다.
- 현재 코드가 H2 + JdbcTemplate으로 일관돼 있어 새 테이블 하나가 가장 적은 결의 변화.
- 단, "선택한다"의 무게가 1·2·3단계와 다르다. **여기서 B를 고른다는 건 "stateless를 포기한다"는 결의가 절반쯤 들어간 선택**이다. 인증된 요청마다 DB 조회가 한 번 더 추가된다. 토큰 쪽에 적용하면 JWT의 stateless가 깨지는 첫 번째 지점이 된다(8번 참고).

**받아들인 트레이드오프:** 인증된 모든 요청에 DB 조회 1회 추가. 세션 쪽은 어차피 `ArgumentResolver`에서 `MemberService.findById()`를 1회 호출하고 있고 — Manager 조회까지 합치면 `/admin/**` 요청은 이미 DB 2회 — 여기에 1회 더 추가되는 수준. 토큰 쪽은 "조회 없음 → 조회 1회"가 0→1의 변화라 더 크게 느껴진다.

**다시 결정할 조건:** 트래픽이 커져 DB 조회가 실제 병목이 되면 C(캐시)로 이동. 단일 서버 + 학습용으로 충분하다고 판단되면 A로 단순화.

### 3.3 검증 시점

| 후보 | 동작 | 장점 | 단점 | 내 선택 |
| --- | --- | --- | --- | --- |
| A. 매 요청마다 저장소 조회 | 인증 추출기에서 memberId 꺼낸 뒤 "이 식별자가 active한가?" 조회 | 즉시 무효화 가능. 정확 | 매 요청 DB 조회 1회 추가. **토큰 방식에서는 stateless 전제가 여기서 깨진다** | 잠정 |
| B. 로그인 시점에만 확인 + 토큰 짧은 만료 | 로그인 시 기존 활성 토큰을 만료 처리하거나 새로 발급. 검증은 서명만 | stateless 유지 (세션은 어차피 매 요청 lookup이라 효과 없음) | **무효화에 최대 만료시간만큼 지연.** 첫 기기는 토큰이 만료될 때까지 계속 접근 가능 → "동시 로그인 방지" 요구를 best-effort로만 만족 | — |

**잠정 선택:** **A (매 요청마다 조회)** — 세션 쪽에는 자연스럽고, 토큰 쪽에는 의도적으로 "여기가 깨지는 지점"임을 받아들이는 선택.

**잠정 선택 이유:** B는 결국 "동시 로그인을 방지한다"의 정의에서 물러서는 길이다. 새 기기에서 로그인했는데 첫 기기가 5분(만료시간)동안 멀쩡히 동작한다면, 요구사항이 풀린 것이 아니다. 가이드도 "stateless 구조가 운영 요구사항과 충돌"을 학습 목표로 명시했다. 그 충돌을 회피(B)하지 말고 정면으로 만나는(A) 게 4단계의 방향.

**세션 쪽에서의 A:** 이미 매 요청 세션 lookup이 일어나고 있으니 "추가 조회"는 active_session 테이블 조회 1회 정도. 큰 결의 변화 없음.

**토큰 쪽에서의 A:** **여기가 진짜 충돌 지점이다.** 토큰을 받고 서명만 검증해서 끝내던 흐름에, "이 토큰이 active 목록에 있는가?" 조회가 매 요청 추가된다. "JWT는 stateless라서 빠르다"의 절반이 사라진다. 이 지점은 8번에서 더 다룬다.

### 3.4 토큰 방식에서의 stateless 포기 여부

| 후보 | 동작 | 트레이드오프 | 내 선택 |
| --- | --- | --- | --- |
| A. 부분적 stateful — 블랙리스트(`jti` 폐기 목록) | 로그아웃·강제 무효화 시 토큰의 `jti`를 블랙리스트에 등록. 매 요청마다 블랙리스트 조회 | 무효화 의미는 명확("이 토큰은 죽었다"). 다만 시간이 지나면 블랙리스트가 계속 쌓임 — TTL을 토큰 만료와 맞춰 자동 정리해야 함 | — |
| **A'. 부분적 stateful — 화이트리스트(`active_token_id` 또는 `token_version`)** | "이 회원의 현재 유효 토큰은 X 하나"를 저장. 새 로그인 시 X 교체 → 기존 토큰은 매 요청 검증에서 탈락 | **동시 로그인 방지에 자연스럽게 맞음(회원당 1개)**. 블랙리스트보다 데이터 작음. 매 요청 조회는 동일 | 잠정 |
| B. 완전 stateless 유지 + 짧은 만료로 우회 | 액세스 토큰을 5분 등으로 짧게. 무효화 = 갱신을 막음 | stateless 유지. **무효화에 최대 만료시간 지연** → 동시 로그인 방지는 best-effort | — |
| C. Refresh Token 모델로 전환 | 짧은 액세스 + 긴 리프레시. 리프레시 서버 저장 + 회수 가능 | 구조가 가장 크게 바뀜. 무효화 정밀도 ↑, 보안성 ↑ — 다만 미션 범위 초과 | — |

**설계상 선택:** **A' (화이트리스트, `active_token_id` 또는 `token_version`)** — 동시 로그인 방지 요구에 가장 자연스럽게 맞아떨어진다. 단, 구현은 하지 않고 설계만.

**선택 이유:**
- 우리의 정책 후보 A·B(3.1) 모두 **"회원당 활성 토큰은 최대 1개"**로 환원된다. 화이트리스트는 이 의미를 자료구조에 그대로 새긴다.
- 블랙리스트(A)는 "버린 것들의 목록"이라 정책과 의미가 한 단계 비뚤어진다("회원당 1개"를 검증하려면 결국 "현재 살아있는 것"을 따로 알아야 함).
- B는 정책을 후퇴시키는 선택이라 4단계 학습 방향과 어긋남.
- C는 구조 자체를 바꾸는 일이라 4단계 범위 초과.

**받아들인 트레이드오프 — 그리고 4단계의 핵심:**
- A'를 채택하는 순간 `TokenAuthenticationExtractor.extractMemberId()`는 **서명 검증만으로 끝낼 수 없다.** "이 토큰 ID가 active한가?"를 저장소에서 조회해야 한다.
- 즉, **JWT를 "stateless이기 때문에" 골랐던 2단계의 전제가 4단계에서 깨진다.** 깨진다는 사실 자체가 4단계의 결과물이다.
- 더불어, JWT 라이브러리는 `jti` 클레임을 표준으로 갖고 있지만 우리 `JwtTokenProvider`는 `memberId`만 담고 있다. 무효화를 도입하면 토큰 발급 코드(`createToken`)도 함께 바뀐다 — `jti` 추가, 발급과 동시에 active 목록에 등록, 이전 토큰 active 목록에서 제거. 발급·검증·만료의 세 지점이 모두 무효화 메커니즘에 결합된다.

**`token_version` 변형:**
- `Member` 테이블에 `token_version INT` 컬럼 추가. 토큰 발급 시 현재 버전을 클레임에 박음. 새 로그인 시 버전 +1. 검증 시 "토큰의 버전 == 회원의 현재 버전" 비교.
- `active_token` 테이블을 안 만들어도 된다는 장점. `MemberService.findById()`가 어차피 매 요청 호출되므로 추가 조회 비용 0.
- 단점: "활성 세션 목록"을 따로 가질 수 없다. "강제 로그아웃" 같은 운영 기능을 만들 때 정보가 부족.

**다시 결정할 조건:** 보안 감사에서 즉시 무효화가 필수로 지적될 때, 또는 모바일 분실/탈취 사고 발생 시. 그 전엔 B(짧은 만료 + 받아들이기)도 합리적 선택지로 남아 있음을 인지.

## 4. 구현 중 새로 마주친 결정들

이번 단계는 코드 구현을 하지 않으므로 "구현 중"이라기보다 "설계 중" 마주친 결정들. 슬롯 3의 표가 다루지 않는 결정들을 모음.

### 4.1 세션·토큰을 한 저장소에 통합 관리할지, 방식별로 분리할지

**문제:** 같은 계정으로 웹 세션 1개 + 모바일 토큰 N개가 공존할 수 있다. "동시 로그인 1개"의 정의가 모호하다.

| 후보 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 방식별 분리 | `active_session(member_id, session_id)`와 `active_token(member_id, jti)`를 별도로 운영. "웹 1개 + 모바일 1개"는 허용 | 자료구조 명확. 두 방식이 독립적으로 진화 가능 | "동시 로그인 1개"라는 운영 요구사항을 글자 그대로 만족하지 못함 — 실제로는 2개 |
| **B. 회원 단위 통합** | `active_auth(member_id, auth_id, type)` 한 테이블에서 둘을 같이 셈 | 정책이 "회원당 1개"로 명료 | **두 방식의 차이가 흐려진다.** 같은 자료구조를 공유하면 "왜 세션과 토큰을 분리해서 운영했지?"라는 질문이 되돌아옴 |
| C. 매니저는 통합(B), 일반 사용자는 분리(A) | 운영 책임이 큰 매니저만 엄격하게 | 보안 민감도에 따른 차등 | 정책 복잡도 ↑. 사용자 등급에 따른 분기 추가 |

**잠정 선택:** **B (회원 단위 통합)** — 단, **이 선택이 2단계의 "공존시킨 이유"와 충돌한다**는 점을 인식하고 멈춤.

**선택 이유와 그것이 만드는 모순:**
- 운영팀의 "같은 계정으로 여러 기기 동시 로그인 방지"는 글자 그대로 읽으면 회원 단위. 방식별 분리(A)는 요구사항을 부분적으로만 만족.
- 그러나 2단계에서 우리는 **"웹은 세션, 모바일은 토큰" 공존을 의도적으로 선택**했다. 이유는 "두 방식의 트레이드오프를 비교하기 위해서"였다. 그런데 B로 가면 둘이 같은 저장소를 공유하게 되고, 두 방식의 차이가 운영 레이어에서는 사라진다.
- **이 모순이 4단계가 만든 가장 중요한 인식**이다. 인증 방식을 골랐던 이유(stateless vs stateful, 공존 vs 통일)와 운영 요구사항(통합 무효화)이 동일 평면에서 부딪힌다.

**미래에 다시 봐야 할 질문 (시간 생겼을 때):**
- A로 가면 "웹 1세션 + 모바일 1토큰" 허용이 보안상 어떤 위협을 만드는가? 매니저 계정 탈취 시나리오를 그려보기.
- B로 통합하면 두 방식이 같은 키 공간(`member_id`)을 공유한다. 세션 ID와 JWT의 `jti`를 같은 컬럼에 둘지, 별도 컬럼에 둘지의 구체적 스키마 설계.
- C(차등) 정책을 도입하면 어디서 분기 판단을 하는가? `Member.role` 같은 필드가 필요? 그것이 3단계 인가 구조와 어떻게 묶이는지.

### 4.2 강제 로그아웃된 클라이언트에게 줄 응답 코드

**문제:** 정책 B(새 로그인 우선)에서 첫 기기가 다음 요청을 했을 때 401만 주면 사용자는 "왜 로그아웃됐지?"를 모른다.

| 후보 | 응답 | 클라이언트 해석 가능성 |
| --- | --- | --- |
| A. 401 (Unauthorized) — 기존과 동일 | `{ "message": "로그인이 필요합니다." }` | 일반 만료와 구분 불가. 사용자는 "또 로그인하라"고만 인식 |
| **B. 401 + 별도 code 필드** | `{ "code": "SESSION_TERMINATED", "message": "다른 기기에서 로그인되어 로그아웃되었습니다." }` | 클라이언트가 메시지를 다르게 표시 가능 |
| C. 419 (Authentication Timeout) 같은 비표준 코드 | 별도 상태 코드 | 표준이 아니라 클라이언트·프록시 호환성 문제 |

**잠정 선택:** **B (401 + code 필드)** — 구현 시 검토.

**선택 이유:** A는 운영 요구사항을 만든 의도("어떤 사용자가 어디에서 로그인 중인지 안다")를 사용자에게도 알려줄 수 있는 기회를 버린다. C는 HTTP 스펙 일관성을 깬다. B는 기존 `GlobalExceptionHandler` 구조에 자연스럽게 들어간다 — `UnauthorizedException`을 상속한 `ForcedLogoutException` 같은 클래스 하나 추가, 응답 직렬화에 `code` 필드 추가.

**확장 방향:** "어느 기기에서 로그인됐는지" 정보까지 같이 줄지(IP, User-Agent, 시각). 이건 `active_session` 테이블 컬럼 설계와 묶임.

---

### 4.3 동시 로그인 방지를 모든 사용자에 적용할지, 매니저에게만 적용할지

**문제:** 일반 사용자에게도 적용하는 게 옳은가?

- 일반 사용자: 자기 예약만 관리. 동시 로그인 자체의 보안 위협이 낮음. 그러나 운영팀 요구사항은 "같은 계정 = 한 사람"이라는 정체성 가정에서 나오므로 일반 사용자에도 적용하는 게 일관적.
- 매니저: 매장 운영 권한 보유. 토큰 탈취 시 매장 단위 피해. 동시 로그인 방지의 보안 가치가 훨씬 큼.

**잠정 결정:** 전체 적용하되, 매니저에게 더 엄격한 정책을 고민할 여지를 남긴다(4.1의 C 후보).

**미래에 봐야 할 질문:** `Member.role`을 도입하지 않고도 매니저 차등을 처리할 수 있는가? `Manager` 도메인이 별도로 있으니, `ManagerCheckInterceptor` 흐름에서 추가 검증을 거는 정도로 충분할 수 있음.

---

### 4.4 테스트로 검증할지, 설계만 정리할지

**결정:** **설계만.**

4단계는 자율이고 학습 목표가 "막힌 지점 이해"임을 반영한 결정. 코드를 짜기 시작하면:
- 인메모리 vs DB 구현체 분기에 시간 소비
- `HttpSessionListener`로 세션 만료 시 레지스트리 정리 같은 곁가지
- `jti` 클레임 추가에 따른 `JwtTokenProvider` API 변경 → 2단계 테스트 전반 영향
- `active_session` DB 스키마 + JdbcRepository 추가 → 미션 범위 초과

가 이어진다. 이 모든 게 "왜 stateless 토큰에서 무효화가 어려운가"를 사고로 이해하는 것보다 학습 가치가 작다.

대신 이 문서가 충분히 자세해야 한다 — **미래의 내가 이 문서만 보고 두 방식의 구현을 다시 그릴 수 있을 만큼.**

## 4.5 미래의 구현을 위한 설계 스케치

> 시간이 생겼을 때 이 절을 출발점으로 코드를 짠다. 세션 쪽과 토큰 쪽을 각각 구체적으로 그려둔다.

### 4.5.1 세션 쪽 구현 스케치 (정책 B "새 로그인 우선" 가정)

**새 컴포넌트:**

```
roomescape.auth.concurrent
  ActiveSessionRegistry              ← 추상 인터페이스
    void register(Long memberId, HttpSession session);
    Optional<HttpSession> find(Long memberId);
    void unregister(Long memberId);
    void unregisterSession(String sessionId);

  InMemoryActiveSessionRegistry     ← 학습용 단일 서버
    Map<Long, HttpSession>
    Map<String, Long>                // sessionId → memberId 역인덱스(만료 정리용)

  JdbcActiveSessionRegistry          ← 운영용(다중 서버 가능)
    table: active_session(member_id PK, session_id_hash, created_at, last_seen_at)
```

**`LoginController.login()` 변경 흐름:**

```
1. memberService.login(email, password) → Member
2. 기존 세션 invalidate (세션 고정 방어, 현재 코드 유지)
3. 새 세션 발급 → newSession
4. registry.find(member.getId()) → 있으면 그 세션 invalidate
   - 이 때 invalidate가 HttpSessionListener를 트리거해
     registry에서도 자동 제거됨 (5번 참고)
5. registry.register(member.getId(), newSession)
6. newSession.setAttribute(SESSION_KEY, member.getId())
```

**`HttpSessionListener` 추가 (필수):**

```java
@Component
class ActiveSessionListener implements HttpSessionListener {
    void sessionDestroyed(HttpSessionEvent se) {
        registry.unregisterSession(se.getSession().getId());
    }
}
```

이게 없으면 **inactivity 만료된 세션의 ID가 registry에 영영 남는다.** 다음 로그인 시 "기존 세션 invalidate" 단계가 죽은 세션 객체를 invalidate하려다 IllegalStateException을 던질 수 있다.

**다음 요청에서 무효화된 세션을 어떻게 감지하나:**
- 첫 기기가 다음 요청을 보내면 쿠키의 JSESSIONID가 이미 invalidate된 세션을 가리킨다.
- `SessionAuthenticationExtractor.supports()`가 `request.getSession(false)`로 false를 받음 → 추출기 통과 안 함 → `LoginCheckInterceptor`가 `UnauthorizedException(401)` 던짐.
- 별도 코드 추가 없이 기존 흐름이 동작한다. **세션 쪽의 매력은 여기 있다.**

**보안 고려:**
- `session_id_hash` — DB에 평문 저장 금지. SHA-256으로 해시해서 저장.
- 검증 시 들어온 세션 ID를 해시해서 비교.

**테스트 시나리오 (미래 작성):**
- 같은 계정 2회 로그인 → 첫 쿠키로 GET /user/reservations → 401
- 같은 계정 2회 로그인 → 두 번째 쿠키로 GET /user/reservations → 200
- 로그아웃 → 다시 로그인 → 정상 (registry가 logout에서도 정리됨을 검증)
- 세션 inactivity 타임아웃 후 → registry에서 자동 제거 (HttpSessionListener 동작 검증)

---

### 4.5.2 토큰 쪽 구현 스케치 — 두 변형

#### 변형 1: `active_token` 화이트리스트

**새 컴포넌트:**

```
roomescape.auth.concurrent
  ActiveTokenRegistry                ← 인터페이스
    void register(Long memberId, String jti);
    boolean isActive(Long memberId, String jti);
    void unregister(Long memberId);

  JdbcActiveTokenRegistry
    table: active_token(member_id PK, jti, issued_at, expires_at)
```

**`JwtTokenProvider.createToken()` 변경:**

```
- 기존: claim(memberId) → signWith → compact
- 변경:
    String jti = UUID.randomUUID().toString();
    String token = Jwts.builder()
        .claim(MEMBER_ID, memberId)
        .id(jti)                          // ← 추가
        .signWith(secretKey, HS256)
        .compact();
    return new IssuedToken(token, jti);   // ← 반환 타입 변경
```

**`MobileLoginController.login()` 변경 흐름:**

```
1. memberService.login() → Member
2. IssuedToken issued = jwtTokenProvider.createToken(member.getId())
3. activeTokenRegistry.register(member.getId(), issued.jti())
   ↑ register 내부에서 UPSERT — 기존 jti가 있으면 덮어씀
4. return new MobileLoginResponse(issued.token(), member.getName())
```

**`TokenAuthenticationExtractor.extractMemberId()` 변경:**

```
- 기존: jwtTokenProvider.extractMemberId(token)
- 변경:
    TokenClaims claims = jwtTokenProvider.parseClaims(token);
                                        // memberId + jti 함께 꺼냄
    if (!activeTokenRegistry.isActive(claims.memberId(), claims.jti())) {
        throw new UnauthorizedException("토큰이 더 이상 유효하지 않습니다.");
    }
    return claims.memberId();
```

**파급 범위:**
- `JwtTokenProvider`의 반환 타입 변경 → `IssuedToken` 또는 별도 메서드 분리
- 2단계 테스트 다수가 `createToken` 반환 String 가정 → 수정 필요
- `application.properties`에 토큰 만료(`security.jwt.expiration-ms`) 추가 — 무효화와 만료가 함께 와야 의미 있음

#### 변형 2: `Member.token_version`

**새 컴포넌트 없음.** `Member`에 컬럼 하나 추가.

**`Member` 변경:**

```sql
ALTER TABLE member ADD COLUMN token_version BIGINT NOT NULL DEFAULT 0;
```

**`JwtTokenProvider.createToken()`:**

```
.claim(MEMBER_ID, memberId)
.claim(TOKEN_VERSION, version)
```

**로그인 시:**

```
member.bumpTokenVersion()              // 도메인 메서드
memberRepository.update(member)
jwtTokenProvider.createToken(member.getId(), member.getTokenVersion())
```

**검증 시:**

```
Long memberId = claims.get(MEMBER_ID, ...)
Long tokenVersion = claims.get(TOKEN_VERSION, ...)
Member current = memberRepository.findById(memberId).orElseThrow(...)
if (current.getTokenVersion() != tokenVersion) {
    throw new UnauthorizedException("토큰이 더 이상 유효하지 않습니다.");
}
```

**장점:**
- 새 테이블 0개. 새 인터페이스 0개. `Member` 조회는 `ArgumentResolver`에서 어차피 일어남(1단계 인사이트 7) → **추가 비용 사실상 0**.
- 화이트리스트 변형보다 훨씬 가벼움.

**단점:**
- "현재 활성 토큰의 정보(jti, 발급 시각, 디바이스)"를 가질 수 없음 → 4.2의 강제 로그아웃 메시지에 "어디서 로그인됐는지"를 못 보여줌.
- 운영 관리 도구를 만들 때(예: "이 사용자가 어디서 로그인 중?") 정보 부족.

**미래의 판단:** 학습용 + 미션 범위 내라면 **변형 2(token_version)가 훨씬 깔끔.** 운영 정보가 필요해지면 변형 1으로 확장.

### 4.5.3 두 방식 통합 운영 스케치 (4.1의 B)

```
table: active_auth(
  id BIGINT PK,
  member_id BIGINT FK,
  auth_type ENUM('SESSION', 'TOKEN'),
  auth_id VARCHAR,       -- session_id_hash 또는 jti
  issued_at TIMESTAMP,
  expires_at TIMESTAMP,
  device_info VARCHAR    -- User-Agent 등
)
unique(member_id)        -- 정책 "회원당 1개"를 DB 제약으로 박음
```

- 로그인 시: `INSERT ... ON CONFLICT(member_id) DO UPDATE` → 자동으로 기존 활성 인증 교체
- 검증 시: `WHERE member_id = ? AND auth_id = ?` 조회
- 강제 로그아웃: `DELETE WHERE member_id = ?`

**unique 제약이 정책을 코드 위에 박는다.** 이게 통합 운영의 가장 큰 매력.

**그러나** 이 unique 제약이 박히는 순간 "세션이 살아있어도 새 모바일 로그인이 세션을 무효화한다." 이게 사용자 입장에서 자연스러운가? 책상의 PC와 손의 폰을 모두 쓰는 일상적 패턴이 막힌다. 정책 B가 운영팀 의도와 맞는지 다시 검증해야 한다. **이 시점에 3.1로 돌아가야 한다** — 정책 미정으로 둔 결정의 실제 의미가 여기서 드러난다.

## 6. 막힌 지점

가장 중요한 섹션. 가이드가 강조한 "어디에서 어려움이 생기는지 이해"의 본체. 세션 쪽과 토큰 쪽을 각각 정리.

### 6.1 세션 쪽 — 막힘이 아니라 "역방향 인덱스 부재"

⚠️ **`HttpSession`은 `sessionId → memberId`만 안다.** 표준 서블릿 API에 `memberId → sessionId` 역방향 조회가 없다. 새 로그인 시 기존 세션을 무효화하려면 이 매핑을 **별도로 유지**해야 한다. 본질적 막힘이 아니라 "추가 자료구조를 어디에 둘 것인가"의 운영적 결정.

⚠️ **이 매핑을 어디에 둘지에 따라 확장성이 갈린다.**
- 인메모리 `Map<Long, HttpSession>`: 단일 서버 학습용으로만 의미.
- DB `active_session` 테이블: 다중 서버 가능. 매 요청 SELECT 추가 비용.
- 서블릿 컨테이너의 외부 세션 스토어(Spring Session + Redis 등): 운영 표준. 인프라 추가.

⚠️ **세션 만료(invalidate)와 레지스트리 정리의 동기화.** `session.invalidate()`가 직접 호출됐을 때(로그아웃, 새 로그인 충돌)는 동시에 레지스트리도 정리해야 한다. 그러나 **세션이 inactivity 만료로 사라지는 경우**(서블릿 컨테이너가 자체적으로 만료시킴)에는 레지스트리에서 자동으로 사라지지 않는다. `HttpSessionListener.sessionDestroyed`를 등록해 만료 이벤트를 받아 레지스트리에서 제거해야 한다. 이 동기화를 빠뜨리면 "이미 죽은 세션의 ID가 active 목록에 남아 새 로그인을 막는" 데드락이 생긴다.

⚠️ **세션 ID를 DB에 저장하는 것의 보안적 함의.** 세션 ID는 사실상 인증 비밀이다. DB에 평문으로 저장하면 DB 덤프 시 모든 활성 세션이 노출된다. 해시(`sha256(session_id)`)로 저장하는 게 안전. 검증할 때도 들어온 세션 ID를 해시해서 비교.

⚠️ **레지스트리와 서블릿 세션 사이의 race condition.** 두 기기가 거의 동시에 로그인을 시도하면, "registry.find → invalidate → register" 사이에 다른 로그인이 끼어들 수 있다. DB unique 제약 또는 명시적 락이 필요. 인메모리라면 `synchronized` 블록. 이 race를 안 보면 "두 세션이 둘 다 active로 남는" 상태가 생길 수 있다.

### 6.2 토큰 쪽 — 본질적 충돌

⚠️ **이미 발급된 JWT는 회수 불가능하다.** JWT는 자기완결적(self-contained)이다. 서명이 유효하고 만료 안 됐으면, 서버는 그 토큰을 거부할 근거가 자체적으로 없다. 동시 로그인 방지를 하려면 **서버가 "거부할 근거"를 외부에 둬야 한다.** 이게 4단계의 진짜 막힘.

⚠️ **무효화 메커니즘은 어떤 형태든 "토큰 외부의 상태"를 요구한다.**
- 블랙리스트: 폐기된 `jti`들의 집합
- 화이트리스트(`active_token_id`): 현재 유효한 토큰 ID
- 토큰 버전(`token_version`): 회원 레코드에 정수 필드 하나. 토큰 발급 시 현재 버전을 클레임에 박고, 검증 시 회원의 현재 버전과 비교

세 가지 모두 **매 요청마다 저장소 조회를 강제한다.** "서명만 검증하면 끝"이라는 JWT의 가장 큰 장점이 사라진다.

⚠️ **`JwtTokenProvider`가 무효화를 모른다.** 현재 `createToken(memberId)`는 무효화에 필요한 식별자(`jti`)를 만들지 않는다. 무효화를 도입하려면:
1. `createToken`이 `jti`를 생성(UUID 등)해 클레임에 추가
2. 생성된 `jti`를 active 저장소에 등록
3. `extractMemberId`가 `jti`도 함께 꺼내 active 여부 조회
4. 새 로그인 시 기존 `jti`를 active에서 제거

발급 시점과 검증 시점, 두 곳 모두에 저장소 의존성이 생긴다. 2단계의 `JwtTokenProvider`는 "외부 의존 0, 시크릿 키만 있으면 동작"이었는데, 이 단순함이 깨진다.

⚠️ **`TokenAuthenticationExtractor`의 책임이 늘어난다.** 현재 이 클래스는 "헤더에서 토큰 꺼내서 검증" 한 가지 일만 한다. 무효화를 도입하면 "active 여부 조회"가 추가된다. 어디까지 `TokenAuthenticationExtractor`의 책임이고, 어디서부터 `TokenValidator` 같은 새 협력자로 분리할지가 설계 문제가 된다.

⚠️ **모바일 클라이언트 입장에서의 UX 어려움.** 강제 무효화된 토큰을 들고 요청한 모바일 앱은 401을 받는다. 그 시점에 앱은 토큰을 버리고 로그인 화면으로 돌아가야 한다. 4.2에서 다룬 응답 코드 분기가 모바일에서 더 중요해진다 — 일반 만료와 강제 무효화를 구분해야 사용자에게 다른 메시지를 줄 수 있다.

⚠️ **만료 정책과의 결합.** 현재 우리 JWT는 `exp`(만료)가 없다(2단계 best-effort 단순화). 무효화를 도입하면 만료도 같이 도입해야 한다. 만료가 없으면 active_token 테이블의 정리(GC)가 안 되어 무한히 쌓인다. 즉, **무효화 도입은 만료 도입과 한 묶음**으로 결정해야 한다.

### 6.3 공존이 만드는 막힘

⚠️ **두 방식을 통합 관리하면 "왜 분리했는가"가 흐려진다.** 4.1에서 다룬 핵심 모순. B(통합)를 선택하면 운영 정책은 깔끔해지지만, 2단계에서 세션·토큰을 의도적으로 공존시킨 학습적 이유가 운영 레이어에서 사라진다.

⚠️ **`AuthenticationExtractor` 추상화 위에 무효화를 어떻게 얹는가.** 2단계 인사이트 1번에서 "바뀌는 건 추출기 한 층뿐"이라고 정리했다. 그러나 무효화는 추출기 안에 들어가는가, 추출기 바깥의 별도 단계인가? 들어가면 두 구현체(Session/Token)가 같은 저장소 조회 로직을 갖게 되어 중복. 바깥에 두면 추상화의 책임 경계가 흐려진다. 깔끔한 답이 없다.

⚠️ **3단계 인가 비용 누적.** `ManagerCheckInterceptor` + `ReservationService`가 이미 Manager 조회를 2회 한다. 여기에 active_session 조회가 추가되면 `/admin/**` 요청 1건당 DB 조회 3회. 운영 요구사항이 늘 때마다 stateless의 성능 이점은 점점 줄어든다. **"운영 요구사항이 stateless를 갉아먹는다"**의 구체적 사례.

⚠️ **테스트 격리 문제.** active_session 또는 active_token 테이블이 추가되면 `IntegrationTest.cleanDatabase()`에 추가해야 한다. 1단계에서 member 테이블 추가 시 cleanDatabase에 빠뜨려 UNIQUE 위반이 났던 그 함정의 반복 가능성. 미래 구현 시 cleanDatabase 동기화를 가장 먼저 챙겨야 한다.

## 7. 알게 된 점

1. **stateless 토큰의 진짜 의미는 "서버가 토큰을 기억할 필요 없음"이 아니라 "서버가 토큰을 기억할 자료구조가 없음"이다.** 전자는 장점, 후자는 운영 요구사항이 오면 단점이 된다. 같은 사실의 양면이다. 2단계에서 토큰을 골랐던 이유가 4단계에서 막힘의 원인이 된다.

2. **세션도 사실은 "역방향 인덱스가 없다"는 같은 종류의 문제를 가졌다.** 다만 세션은 이미 서버가 상태를 들고 있으므로, 인덱스를 추가하는 게 "기존 상태에 인덱스 하나 더"인 반면, 토큰은 "없던 상태를 새로 만든다"라 결의 변화가 크다. 같은 문제의 두 다른 깊이.

3. **운영 요구사항은 인증 방식 선택을 사후적으로 평가한다.** 처음 인증 방식을 고를 때는 보통 "기본 인증 + 로그아웃" 정도만 본다. 동시 로그인 방지, 강제 로그아웃, 디바이스 별 관리 같은 요구가 추가되면 그제야 처음 선택의 비용이 드러난다. 미래의 운영 요구사항을 다 예측할 수는 없지만, **"확장 시 비용이 어디로 가는가"**는 첫 선택 시점에 그릴 수 있어야 한다.

4. **"stateless" vs "stateful"은 이진이 아니라 스펙트럼이다.** 완전 stateless(서명만 검증) → 부분적 stateful(jti 화이트리스트 매 요청 조회) → 완전 stateful(세션 + 서버 메모리). JWT + 블랙리스트는 가운데 어딘가다. 가운데로 가는 순간 양쪽의 장점을 부분적으로만 가진다 — stateless의 빠름도 아니고, stateful의 명료함도 아닌.

5. **충돌 정책(3.1)은 인증 방식과 직교한다.** 정책 A·B를 선택하는 일과 그 정책을 세션·토큰 위에서 구현하는 일은 다른 문제다. 한쪽 정책을 가정하고 시작하면 "이 정책이라서 토큰이 어렵다"는 잘못된 결론에 도달하기 쉽다. **어떤 정책이든 세션 위에서는 "메커니즘이 있다(만든다)"가 되고 토큰 위에서는 "메커니즘이 없다(새로 만들어야 한다)"가 된다.** 이 비대칭이 인증 방식의 본질적 차이다.

6. **3단계 인가의 "이중 조회" 문제가 4단계에서 더 커진다.** `ManagerCheckInterceptor` + `ReservationService`의 Manager 조회 중복은 3단계에서 "불편하지만 분리된 책임의 대가"로 정리됐다. 4단계에서 active_session 조회가 추가되면 한 요청에 DB 3회가 된다. 운영 요구사항이 누적될수록 토큰 클레임에 정보를 임베드하고 싶은 압력이 커지지만, 임베드하면 stale 데이터 문제가 따라온다(3단계 9번이 이미 던진 질문). 무효화 메커니즘이 있어야 클레임 임베드가 안전해지는데, 그 무효화가 또 매 요청 조회를 요구한다. **여기에서 빠져나갈 깔끔한 길이 없다는 사실 자체가 학습.**

7. **"공존"이라는 선택의 청구서가 4단계에서 두 번째로 온다.** 2단계는 첫 청구서("모바일에서 쿠키가 어색하다 → 토큰 도입"). 4단계는 두 번째 청구서("두 방식을 통합 관리하려면 분리했던 이유가 흐려진다"). 첫 청구서는 비교 학습 효과로 갚을 가치가 있었다. 두 번째 청구서는 학습 효과보다는 "여기서 멈춰서 어렵다는 사실을 인식하는 것"이 갚는 방법이다.

8. **무효화는 만료와 한 묶음이다.** active_token 화이트리스트를 만들려면 만료 정책이 필수다. 만료 없는 토큰은 active_token 테이블을 무한히 키우고, 정리 시점을 정할 수 없다. 2단계에서 만료를 단순화로 빼둔 결정이 4단계에서 짝궁을 찾으러 돌아온다.

9. **`token_version` 변형의 의외성.** 새 테이블 없이 `Member` 컬럼 하나만으로 토큰 무효화가 된다는 사실은 처음 떠올리기 어렵다. 화이트리스트·블랙리스트 같은 자료구조 중심 사고에서 벗어나 "토큰의 유효성 = 회원 상태의 단조 증가하는 값과 일치"라는 다른 모델로 환원하는 것. **자료구조보다 불변식이 단순한 해법인 경우.**

## 8. 토큰의 stateless 특성이 깨지는 지점

가이드 학습 목표 핵심. JWT의 stateless가 어디서 무너지는지 짚는다.

### 8.1 무엇이 "stateless"인가 — 정의의 좁힘

JWT를 stateless라고 부르는 이유는 **"서버가 토큰의 발급 사실을 기억하지 않아도 검증이 가능하다"**는 한 가지 속성 때문이다.
- 페이로드(memberId, role 등) 자체에 정보가 들어있다.
- 서명으로 무결성을 보장한다.
- 만료(`exp`)는 토큰 자체가 들고 있다.

이 한 가지 속성 덕분에:
- 인증 서버와 리소스 서버가 분리될 수 있다(서명 키만 공유하면 됨).
- 수평 확장 시 인증 상태 동기화 부담이 없다.
- DB/캐시 조회 없이 인증이 끝난다.

### 8.2 동시 로그인 방지가 깨는 것

동시 로그인 방지 = "이미 발급된 토큰을 무효화할 수 있어야 함." 이걸 달성하려면 **서버가 "어떤 토큰이 현재 유효한지"를 알아야 한다.** 이 순간 위의 한 가지 속성이 깨진다.

| stateless 속성 | 무효화 도입 후 |
| --- | --- |
| 서버는 토큰 발급 사실을 기억하지 않아도 됨 | **기억해야 함** (active_token 또는 blacklist) |
| 페이로드 + 서명으로 검증 완료 | **+ 저장소 조회**가 매 요청 필요 |
| 인증 서버 ↔ 리소스 서버 분리 가능 | **공유 저장소** 필요 |
| 수평 확장 시 상태 동기화 부담 0 | **저장소가 분산 동기화 책임** 짊어짐 |
| DB/캐시 조회 없이 인증 종료 | **조회 1회 추가** (성능상 세션과 거의 동등) |

### 8.3 "그래도 stateless인가"의 미묘한 답

깨졌다고 말하는 것도, 유지된다고 말하는 것도 둘 다 부분적으로 맞다.
- **여전히 stateless인 부분:** 페이로드에 사용자 정보가 들어있어 클라이언트가 정체성을 들고 다닌다. 토큰 자체는 자기완결적이다.
- **stateless가 아닌 부분:** 검증이 토큰만으로 완결되지 않는다. 외부 상태 조회가 필수.

**그래서 정확한 표현은 "self-contained payload + stateful invalidation".** "stateless"라는 한 단어로 부르기엔 모호하다.

### 8.4 stateless를 살리려는 시도들과 그 한계

- **짧은 만료 + Refresh Token:** 액세스 토큰은 stateless로 유지. 무효화는 Refresh로 위임. 그러나 무효화 지연(액세스 만료까지)이 남고, Refresh 자체는 stateful(서버에 저장 + 회수 가능)이라야 의미가 있다. **무효화 책임을 다른 토큰으로 옮긴 것이지 없앤 게 아니다.**
- **토큰 버전(`token_version`):** 회원 레코드에 정수 컬럼 하나. 토큰 발급 시 현재 버전을 클레임에 박고, 검증 시 회원의 현재 버전과 비교. 무효화 = 버전 증가. **회원 조회는 어차피 자주 일어나므로 추가 비용이 0에 가깝다.** 단, 이것도 결국 매 요청 회원 조회를 강제한다는 점에서 stateless가 아니다.
- **분산 캐시(Redis) + 짧은 만료:** 매 요청 조회를 캐시에 위임해 성능 비용을 줄임. stateless의 의미는 여전히 깨졌지만 실용적으로는 거의 stateless에 가깝게 동작. 가장 흔한 실무 패턴.

### 8.5 결론

JWT의 "stateless"는 **"운영 요구사항이 없을 때만 stateless"**다. 동시 로그인 방지, 강제 로그아웃, 디바이스별 관리 같은 요구사항이 추가되는 순간 stateless의 정의를 좁혀서 유지하거나, 좁힘마저 포기해야 한다. 둘 다 "JWT를 stateless 때문에 선택했다"는 처음 동기와 부분적으로 어긋난다.

**이것이 4단계 학습 목표 마지막 항목("stateless한 구조가 운영 요구사항과 충돌할 수 있음을 이해")의 본체.**

## 9. 다시 한다면 바꾸고 싶은 점

- **인증 방식 자체를 세션 단일로 했으면** 동시 로그인 방지가 단순했을 것이다. `Map<MemberId, HttpSession>` 하나 추가하면 끝나는 일. 그러나 모바일이 쿠키를 어색하게 다루는 문제는 다시 돌아오므로 단일 방식의 다른 비용이 있다.
- **인증 방식 자체를 토큰 단일 + Refresh Token으로 했으면** 동시 로그인 방지가 Refresh 회수로 깔끔히 풀린다. 다만 미션 범위를 크게 벗어났을 것 — 2단계가 "토큰 도입"이 아니라 "Refresh Token 시스템 설계"가 됐을 것.
- **2단계에서 토큰에 `jti`를 미리 넣어뒀으면** 4단계에서 토큰 무효화 도입의 결의가 작아진다. "필요해진 후 추가"는 클레임 구조 변경이라 기존 토큰을 다 무효화해야 한다. 다만 미리 넣는 건 "필요하지 않은 걸 넣는다"는 점에서 YAGNI 위반.
- **2단계에서 토큰 만료(`exp`)를 단순화로 빼지 말았어야 했을 수도.** 만료가 있어야 무효화 메커니즘(active_token GC)이 자연스러워진다. 단순화의 청구서가 여기서도 옴.
- **3.1 충돌 정책을 미정으로 둔 결정 자체는 유지.** 학습 목표에 맞고, 어느 쪽을 골라도 핵심 비대칭은 같다.
- **세션·토큰 통합 관리(4.1 B) 결정도 잠정으로만 유지.** 정말 미래에 구현할 때, "분리 운영의 학습 가치는 이미 거뒀고 운영 단순성이 더 중요하다"는 판단을 그 시점에 다시 한다.

## 10. 평가 기준 충족 한 줄씩

1. **공통 처리 분리:** `AuthenticationExtractor` 추상화는 이미 2단계에서 완성. 4단계는 그 위에 "무효화" 단계를 어떻게 얹을지를 설계 차원에서 검토. 추출기 안에 넣을지 바깥에 분리할지의 책임 경계 문제를 6.3에서 다룸.
2. **다른 후보와 비교 설명:** 슬롯 3 네 칸 모두 후보 표 + 트레이드오프 기록. 슬롯 4도 추가 결정 4개에 대해 후보를 비교. 특히 3.4(stateless 포기 여부)는 블랙리스트 / 화이트리스트 / 짧은 만료 / Refresh Token 네 후보를 비교해 화이트리스트를 설계상 선택한 이유 정리. 토큰 쪽 구현 변형도 화이트리스트 / token_version 둘을 비교(4.5.2).
3. **트레이드오프 인식:** "세션 = 본질적 막힘 없음, 인덱스 부재가 운영 문제로 환원" / "토큰 = 본질적 충돌, 무효화 도입 시 stateless 전제 붕괴" / "통합 관리 = 운영 단순성 ↔ 공존 학습 의미 흐려짐" 세 축 모두 손끝으로 인식.
4. **운영 위협 시나리오 경험:** ← 이번 단계의 핵심. 4.2(강제 로그아웃 UX), 6.2(토큰 탈취 시 회수 불가), 6.3(인가 비용 누적, race condition, 테스트 격리), 8(stateless가 운영 요구사항에 무너지는 지점)에서 운영 시나리오를 구체적으로 그리고 어디서 어떤 비용이 발생하는지 정리.

## 10.5 "생각해 볼 점"에 대한 4단계 최종 답변

### Q1. 서버는 현재 로그인한 사용자의 상태를 알고 있는가?

**절반만.** 세션 쪽은 `HttpSession`이 서버에 살아있어 원칙상 알 수 있지만, `memberId → sessionId` 역방향 인덱스가 없어 "이 회원의 활성 세션을 찾아라"는 못 한다. 토큰 쪽은 전혀 모른다 — JWT는 발급 후 서버가 추적하지 않는다. 두 방식 모두 동시 로그인 방지 요구가 오기 전까지는 "알 필요가 없었다"가 정확.

### Q2. 새 로그인이 발생했을 때 기존 로그인 정보를 찾을 수 있는가?

현재 구조에서는 **세션 쪽도 토큰 쪽도 못 찾는다.** 세션은 역방향 인덱스를 추가해야 가능(인메모리 Map 또는 active_session 테이블). 토큰은 화이트리스트 / 블랙리스트 / token_version 중 하나를 도입해야 가능. 어느 쪽이든 **현재 코드에 없는 새로운 자료구조**를 추가해야 한다.

### Q3. 이미 발급된 토큰을 무효화할 수 있는가?

**현재 구조에서는 불가능.** JWT는 자기완결적이라 서명만으로 검증이 끝나고, 서버에 "이 토큰은 죽었다"고 기록할 곳이 없다. 무효화하려면 외부 저장소(블랙리스트 또는 화이트리스트)를 도입해야 하고, 도입하는 순간 매 요청마다 그 저장소를 조회하게 되어 stateless의 전제가 깨진다.

### Q4. 토큰을 검증할 때마다 서버 저장소를 확인하면 여전히 stateless하다고 볼 수 있는가?

**부분적으로만.** 페이로드가 자기완결적이라는 의미에서는 stateless이지만, 검증이 토큰만으로 완결되지 않는다는 의미에서는 stateless가 아니다. 정확한 표현은 "**self-contained payload + stateful invalidation**". "stateless"라는 한 단어로 부르기엔 모호하다. 이 모호함을 인식하는 것이 4단계 학습의 핵심.

### Q5. 운영 요구사항을 만족하기 위해 어떤 상태를 추가로 저장해야 하는가?

세션 쪽: `Map<MemberId, SessionId>` 또는 `active_session(member_id, session_id_hash, ...)` 테이블. 영속성·다중 서버·만료 동기화를 어디까지 챙기느냐에 따라 인메모리 / DB / Redis 선택지.

토큰 쪽: `active_token(member_id, jti, expires_at)` 화이트리스트 또는 `Member.token_version` 단일 정수 컬럼. 매 요청마다 이 저장소를 조회한다는 비용을 받아들여야 한다.

공존 운영: 둘을 통합한 `active_auth(member_id, auth_id, type, expires_at)` 한 테이블. 단, 통합하면 두 방식을 의도적으로 분리했던 학습 이유가 운영 레이어에서 사라진다는 모순을 받아들여야 한다.

**핵심: 어떤 형태든 "회원 단위로 활성 인증을 추적하는 상태"가 추가된다. JWT의 stateless 전제는 이 추가와 양립하지 않는다.**
