# 00. 학습 개요 — 방탈출 인증/인가 미션

> 이 문서는 "지금 내가 무엇을, 왜, 어떻게 배우고 있는가"를 잊지 않기 위한 지도다.
> 다음 단계로 넘어가기 전마다 한 번씩 다시 읽는다.

---

## 1. 미션의 본질

이 미션의 중심은 **"인증/인가를 많이 아는 것"이 아니다.**
미션 가이드가 명시한 두 가지가 전부다.

1. **자기 코드 위에 인증/인가를 직접 적용한다.**
2. **선택지 사이의 트레이드오프를 자기 손끝으로 경험한다.**

따라서 이 학습의 성공 기준은 "동작하는 코드"가 아니라, 다음 문장을 막힘 없이 말할 수 있는지다.

> "나는 ___을 선택했다. 다른 후보는 ___이었다. 이 방식을 선택한 이유는 ___이다.
> 구현하면서 불편했던 점은 ___이었고, 요구사항이 ___로 바뀌면 ___ 부분이 흔들린다."

---

## 2. 미션 서사 (요약)

```
[과거]   작은 매장 1개  →  이름 입력만으로 예약
[현재]   여러 매장 + 매장별 매니저 + 모바일 앱 확장

본사 요구사항:
1. 누가 예약을 만들고 수정하는지 알아야 한다.       → 인증 (1단계)
2. 매장 매니저는 자기 매장 예약만 관리해야 한다.    → 인가 (3단계)
3. 웹뿐 아니라 모바일 앱에서도 예약 관리가 가능해야. → 모바일 (2단계)
4. (운영팀) 동시 로그인을 막아 달라.                  → 동시로그인 (4단계, 자율)
```

이 서사가 곧 단계 구조다.

---

## 3. 4단계 + 공유회 큰 그림

각 단계의 **목표 / 요구사항 / 구현 조건 / 구현 시 선택할 것 / 생각해 볼 점 / 완료 기준**을 가이드 원문 그대로 풀어둔다. 단계에 들어가기 직전마다 해당 단계만 다시 읽으면 된다.

### 한눈에 보기

| 단계 | 주제 | 핵심 질문 | 새로 도입되는 것 |
|---|---|---|---|
| **1단계** | 웹 로그인 (인증) | 로그인 상태를 어떻게 유지하고, 그 정보를 코드에 어떻게 전달할 것인가? | `Member` 도메인, 로그인/로그아웃 API, 인증 공통 처리 도구 (Interceptor / ArgumentResolver / Filter 중 선택), `UnauthorizedException(401)` |
| **2단계** | 모바일 인증 확장 | 웹 인증을 그대로 확장할 것인가, 모바일에 맞는 방식을 선택할 것인가? | 토큰 방식(또는 다른 선택), 쿠키 vs 헤더, 웹/모바일 인증 흐름의 통합 또는 분리 |
| **3단계** | 인가 | 인가 판단을 **어디**에, **무엇**으로 두는가? | `Store` / `Manager` 개념, `ForbiddenException(403)`, 인가 실패 응답 정책(403 vs 404) |
| **4단계** *(자율)* | 동시 로그인 방지 | stateless한 토큰 구조가 운영 요구사항과 충돌하면 어떻게 풀 것인가? | 토큰 무효화 전략 또는 서버 측 세션/세션 ID 관리 |
| **공유회** | 같은 요구사항, 다른 선택 비교 | 내 선택을 설명하고, 다른 사람의 선택을 듣고, 유지/변경을 결정한다. | (산출물 정리) |

> 4단계는 "완성"보다 "어디에서 막혔는지 이해하는 것"이 목표다. 부담 없이 접근한다.

---

### 1단계 — 웹에서 로그인하기 (인증)

**미션 배경.** 이름 입력 기반 식별은 빠르게 만들기엔 좋지만 신뢰할 수 없다. 다른 사람의 이름을 입력할 수 있고, 동명이인 문제도 있다. 이름 입력 기반 예약 흐름을 **로그인 사용자 기반** 예약 흐름으로 바꾼다.

**🎯 목표**
- 사용자가 웹에서 로그인할 수 있다.
- 로그인한 사용자를 기준으로 예약을 생성한다.
- 로그인한 사용자를 기준으로 예약을 조회한다.
- 로그인하지 않은 사용자는 인증이 필요한 기능을 사용할 수 없다.
- 인증 로직이 컨트롤러마다 반복되지 않게 한다.

**📋 요구사항**

*로그인*
- 사용자는 로그인할 수 있다.
- 로그인에 성공하면 이후 요청에서 같은 사용자를 식별할 수 있어야 한다.
- 로그인에 실패하면 적절한 응답을 반환한다.

*예약 생성*
- 로그인한 사용자는 예약을 생성할 수 있다.
- 예약 생성 시 요청으로 받은 이름이 아니라 **로그인한 사용자**를 기준으로 예약을 만든다.
- 로그인하지 않은 사용자는 예약을 생성할 수 없다.

*예약 조회*
- 로그인한 사용자는 자신의 예약을 조회할 수 있다.
- 로그인하지 않은 사용자는 인증이 필요한 예약 조회 기능을 사용할 수 없다.

*인증 공통 처리*
- 로그인 여부 확인 로직을 컨트롤러마다 반복하지 않는다.
- 인증이 필요한 API와 필요하지 않은 API를 구분한다.
- 인증 실패 시 일관된 응답을 반환한다.

**⚙️ 구현 조건**
- Spring Security를 사용하지 않는다.
- 세션 또는 직접 구현한 인증 흐름을 사용할 수 있다.
- 인증에 필요한 공통 처리는 Interceptor, ArgumentResolver 등 적절한 도구를 사용해 분리한다.
- 컨트롤러는 가능한 한 로그인 사용자 정보를 직접 꺼내지 않는다.

**🔀 구현 시 선택할 사항** (= 핵심 결정 카테고리, 실제로는 각 안에서 더 갈라짐)
- **로그인 상태 유지 방식** — 세션 / 직접 만든 토큰 / 그 외
- **인증이 필요한 API 구분 방식** — 경로 패턴 / 어노테이션 / 별도 정책
- **인증 공통 처리 위치** — Interceptor / ArgumentResolver / 두 도구 조합 / Filter / 그 외
- **컨트롤러에 로그인 사용자 전달 방식** — 세션 직접 조회 / `LoginMember` 같은 별도 객체 주입
- **인증 실패 응답 방식** — 어떤 상태 코드, 어떤 메시지 본문

> 공유회에서 비교되는 건 "로그인을 구현했는가"가 아니라 **"왜 그 방식으로 상태를 유지했고, 왜 그 위치에서 인증을 처리했는가"**.

**🤔 생각해 볼 점**
- 로그인 상태는 어디에 저장할 것인가?
- 요청마다 사용자를 어떻게 확인할 것인가?
- 컨트롤러가 세션이나 요청 헤더를 직접 다루는 것이 적절한가?
- 인증 실패와 잘못된 요청은 어떻게 구분할 것인가?
- 기존 이름 입력 필드는 어디까지 제거하거나 대체할 수 있는가?

**✅ 완료 기준**
- 로그인한 사용자를 기준으로 예약을 생성한다.
- 로그인하지 않은 요청은 인증이 필요한 기능을 사용할 수 없다.
- 인증 로직이 여러 컨트롤러에 중복되어 있지 않다.
- 인증 실패 상황을 테스트했다.

**📝 PR 본문 양식**
```
로그인 상태 유지 방식:
인증이 필요한 API:
공통 처리 위치:
테스트한 인증 실패 상황:
```

### 2단계 — 모바일 앱 요청에서도 로그인 유지하기

**미션 배경.** 서비스가 모바일 앱으로 확장된다. 웹에서 쓴 인증 방식이 모바일 앱에도 그대로 적절한지 검토해야 한다. **브라우저와 모바일 앱은 인증 정보를 저장하고 전달하는 방식이 다를 수 있다.**

**🎯 목표**
- 모바일 앱 요청에서도 로그인한 사용자를 식별한다.
- 모바일 앱 사용자가 인증이 필요한 API를 사용할 수 있게 한다.
- 인증 정보가 없거나 유효하지 않은 요청을 거부한다.
- 웹 인증 구현과 모바일 인증 구현의 **공통점과 차이점**을 설명한다.
- 세션과 토큰 중 선택한 방식의 이유를 설명한다.

**📋 요구사항**

*모바일 로그인*
- 모바일 앱 사용자는 로그인할 수 있다.
- 로그인 성공 후 모바일 앱이 이후 요청에서 사용할 인증 정보를 받을 수 있어야 한다.
- 인증 정보는 이후 요청마다 서버가 사용자를 식별할 수 있는 형태여야 한다.

*모바일 인증 요청*
- 모바일 앱은 인증이 필요한 API를 호출할 때 인증 정보를 함께 전달한다.
- 서버는 전달된 인증 정보를 검증한다.
- 인증 정보가 유효하면 로그인한 사용자로 요청을 처리한다.
- 인증 정보가 없거나 유효하지 않으면 요청을 거부한다.

*웹 인증과의 관계*
- 웹 인증 흐름과 모바일 인증 흐름이 어떤 점에서 같은지 설명할 수 있어야 한다.
- 웹 인증 흐름과 모바일 인증 흐름이 어떤 점에서 다른지 설명할 수 있어야 한다.
- 가능한 한 중복된 인증 로직을 줄인다.

**⚙️ 구현 조건**
- 세션과 토큰 중 하나를 선택하거나, 두 방식을 조합할 수 있다.
- 선택한 방식 외의 다른 후보도 검토한다.
- 인증 정보를 전달하는 위치를 명확히 정한다.
- 컨트롤러는 웹인지 모바일인지에 따라 인증 로직이 과도하게 갈라지지 않도록 한다.

**🔀 구현 시 선택할 사항**
- **모바일 요청의 인증 방식** — 세션 유지 / 토큰 발급 / 웹과 다르게 처리
- **인증 정보 전달 위치** — 쿠키 / `Authorization` 헤더 / 별도 헤더
- **웹/모바일 인증 흐름의 통합 방식** — 같은 검증 로직 재사용 / 클라이언트별 어댑터
- **만료와 로그아웃 처리 방식** — 서버에서 상태 제거 / 토큰 만료 시간에 맡김 / 별도 무효화 저장소
- **인증 실패 응답 방식** — 웹/모바일 동일 / 클라이언트별 분리

> 공유회 비교 포인트는 "세션이냐 토큰이냐"만이 아니다. **선택한 방식이 웹과 모바일 요청을 얼마나 일관되게 설명하는지, 로그아웃·만료 운영 상황에서 어떤 불편이 생기는지** 까지 본다.

**🤔 생각해 볼 점**
- 브라우저와 모바일 앱은 인증 정보를 어떻게 다르게 다루는가?
- 세션을 모바일 앱에서 그대로 사용하면 어떤 점이 편하고 어떤 점이 불편한가?
- 토큰을 사용하면 어떤 점이 편하고 어떤 점이 불편한가?
- 로그아웃과 만료는 어떻게 처리할 것인가?
- 서버가 상태를 기억하는 방식과 기억하지 않는 방식은 어떤 차이가 있는가?

**✅ 완료 기준**
- 모바일 앱 요청에서도 로그인한 사용자를 식별할 수 있다.
- 인증 정보가 없거나 유효하지 않은 모바일 요청을 거부한다.
- 선택한 인증 방식과 다른 후보를 비교해 설명했다.
- 웹 인증 흐름과 모바일 인증 흐름의 공통점과 차이점을 설명했다.

**📝 PR 본문 양식**
```
선택 도구:
다른 후보:
선택 이유:
불편하거나 아쉬운 점:
```

### 3단계 — 인가: 자기 매장 예약만 관리하기

**미션 배경.** 여러 매장과 매장별 매니저. 매니저는 자기 매장 예약만 관리해야 한다. **로그인했다고 모든 예약에 접근할 수 있는 건 아니다.** 인증을 넘어 인가가 필요하다.

**🎯 목표**
- 인증과 인가를 **구분**한다.
- 로그인한 매니저가 어떤 매장에 속해 있는지 확인한다.
- 접근하려는 예약이 어떤 매장에 속해 있는지 확인한다.
- 매장 매니저가 자기 매장의 예약만 관리할 수 있게 한다.
- 인가 실패와 인증 실패를 **구분해** 처리한다.

**📋 요구사항**

*매장 매니저 식별*
- 로그인한 사용자가 매장 매니저인지 확인할 수 있어야 한다.
- 매장 매니저가 어떤 매장을 관리하는지 확인할 수 있어야 한다.

*예약 접근 제한*
- 매장 매니저는 자기 매장의 예약만 조회할 수 있다.
- 매장 매니저는 자기 매장의 예약만 변경할 수 있다.
- 매장 매니저는 자기 매장의 예약만 삭제할 수 있다.
- 다른 매장의 예약에 접근하려는 요청은 거부한다.

*실패 처리*
- 로그인하지 않은 요청은 **인증 실패**로 처리한다.
- 로그인했지만 권한이 없는 요청은 **인가 실패**로 처리한다.
- 인증 실패와 인가 실패를 같은 문제로 뭉개지 않는다.

**⚙️ 구현 조건**
- 로그인한 사용자가 어떤 매장에 속해 있는지 확인할 수 있어야 한다.
- 접근하려는 예약이 어떤 매장에 속해 있는지 확인할 수 있어야 한다.
- 두 정보를 비교해 요청을 허용하거나 거부한다.
- 인가 판단 로직이 컨트롤러에 과도하게 흩어지지 않도록 한다.

**🔀 구현 시 선택할 사항**
- **인가 판단 위치** — Controller에서 먼저 막기 / Service에서 검증 / 도메인 객체의 규칙으로 표현
- **매장 매니저와 매장의 관계 표현 방식** — 1:1 (매니저 하나에 매장 하나) / 1:N (여러 매장 관리)
- **예약 접근 권한 확인 방식** — 예약 조회 후 매장 권한 비교 / 처음부터 권한 조건 포함해 조회
- **인가 실패 응답 방식** — 403 권한 없음 / 404 리소스 숨기기
- **인증 정보와 도메인 정보의 연결 방식** — 로그인 사용자 ID로 매니저를 조회 / 로그인 객체에 매장 정보 포함

> 공유회 비교 포인트는 "권한 체크를 했는가"가 아니라 **"왜 그 계층에서 인가를 판단했고, 요구사항이 바뀌면 어느 부분이 흔들리는가"**.

**🤔 생각해 볼 점**
- 인가 판단은 Controller / Service / Domain 중 어디에 두는 것이 적절한가?
- 예약 조회와 예약 변경에서 인가 판단 위치가 달라질 수 있는가?
- 인가 실패 시 어떤 응답을 반환할 것인가?
- 매장 매니저가 여러 매장을 관리하게 되면 구조를 어떻게 바꿀 것인가?
- 인증된 사용자 정보를 인가 판단에 어떻게 전달할 것인가?

**✅ 완료 기준**
- 매장 매니저는 자기 매장의 예약만 관리할 수 있다.
- 다른 매장 예약에 접근하는 요청은 거부된다.
- 인증 실패와 인가 실패가 구분된다.
- 인가 판단 위치와 선택 이유를 설명했다.

**📝 PR 본문 양식**
```
선택 도구:
다른 후보:
선택 이유:
인가 판단 위치:
유지하거나 변경하고 싶은 점:
```

### 4단계 — 동시 로그인 방지 (자율)

**미션 배경.** 운영팀에서 *"같은 계정으로 여러 기기에서 동시에 로그인하지 못하게 해 주세요"* 라는 요청. 단순해 보이지만 인증 방식에 따라 구현 난이도가 달라진다. 특히 **토큰을 쓰면 서버가 로그인 상태를 기억하지 않는 구조와 충돌**한다.

> 자율 단계. **완성보다 "어디에서 어려움이 생기는지 이해"가 목표.**

**🎯 목표**
- 동시 로그인 방지 요구사항이 인증 방식과 어떻게 연결되는지 이해한다.
- 세션 방식에서 동시 로그인을 제한하는 방법을 검토한다.
- 토큰 방식에서 이미 발급된 토큰을 무효화하는 어려움을 경험한다.
- stateless한 구조가 운영 요구사항과 충돌할 수 있음을 이해한다.

**📋 요구사항**
- 같은 계정으로 여러 기기에서 동시에 로그인하는 상황을 제한한다.
- 새 로그인이 발생했을 때 기존 로그인 상태를 어떻게 처리할지 정한다.
- 기존 로그인을 유지할지, 새 로그인을 우선할지 정책을 정한다.
- 세션 또는 토큰 방식에서 이 요구사항을 구현할 때 어떤 어려움이 있는지 정리한다.

**⚙️ 구현 조건**
- 어떤 지점에서 어려웠는지 설명하면 된다. (코드 완성 강제 아님)
- 현재 미션에서 선택한 인증 방식을 기준으로 먼저 검토한다.

**🔀 구현 시 선택할 사항**
- **충돌 정책** — 기존 로그인 유지 / 새 로그인 우선
- **상태 저장 위치** — 인메모리 / DB / 별도 캐시 저장소
- **검증 시점** — 매 요청마다 / 로그인 시점에만
- **토큰 방식에서의 stateless 포기 여부** — 부분적 stateful로 전환 / 완전 stateless 유지하며 우회

**🤔 생각해 볼 점**
- 서버는 현재 로그인한 사용자의 상태를 알고 있는가?
- 새 로그인이 발생했을 때 기존 로그인 정보를 찾을 수 있는가?
- 이미 발급된 토큰을 무효화할 수 있는가?
- 토큰을 검증할 때마다 서버 저장소를 확인하면 여전히 stateless하다고 볼 수 있는가?
- 운영 요구사항을 만족하기 위해 어떤 상태를 추가로 저장해야 하는가?

**✅ 완료 기준**
- 동시 로그인 방지 요구사항을 현재 인증 방식에서 검토했다.
- 구현하거나 설계한 방식을 설명했다.
- 막힌 지점과 알게 된 점을 정리했다.
- 토큰의 stateless한 특성이 깨질 수 있는 지점을 인식했다.

**📝 PR 본문 양식**
```
시도한 방식:
막힌 지점:
알게 된 점:
다시 한다면 바꾸고 싶은 점:
```

### 공유회 — 같은 요구사항, 다른 선택 비교하기

**🎯 공유회의 목적.** 구현 결과 발표가 아니다. 같은 요구사항을 해결하면서 **각자가 어떤 선택을 했는지 비교**하는 자리다. 정답을 찾지 않는다. 자기 선택을 설명하고, 다른 사람의 선택을 듣고, **내 구현을 유지할지 바꿀지 판단**한다.

**비교 지점 5개** (각 단계 선택지가 여기로 모인다)
1. **로그인 상태 유지 방식** — 어디에 저장했는가, 세션/토큰/그 외, 그 이유, 로그아웃·만료 처리 난이도
2. **인증 공통 처리 위치** — Interceptor / ArgumentResolver / Filter / 조합, 둘 다 썼다면 역할 분리 방식, 컨트롤러에 남은 인증 코드의 이유
3. **모바일 앱 요청 인증 방식** — 쿠키 / Authorization 헤더, 웹/모바일 통합 vs 분리, 모바일에서 불편했던 점
4. **인가 판단 위치** — Controller / Service / Domain, 조회 후 비교 vs 권한 조건 포함 조회, 매니저 1:1 → 1:N 확장 영향
5. **실패 응답 설계** — 401 vs 403 vs 404 구분, 리소스 숨김 vs 명시적 거절

**공유회 원칙**
- 구현량을 자랑하지 않는다.
- 정답을 맞히려 하지 않는다.
- 선택한 이유와 불편했던 점을 함께 말한다.
- 다른 사람의 선택을 그대로 따라 하지 않는다.
- 자기 서비스의 요구사항과 코드 구조를 기준으로 판단한다.
- 바꾸지 않기로 했다면 유지하는 이유를 설명한다.

**공유회 진행 흐름**
1. **개인 정리** (5분) — "나는 ___을 선택했다. 다른 후보는 ___이었다. 이유는 ___이다."
2. **그룹 공유** (각 5분) — 선택 / 다른 후보 / 이유 / 불편했던 점 / 묻고 싶은 점
3. **비교 질문 고르기** — 그룹에서 가장 선택이 갈린 질문 하나
4. **선택 비교 표 작성** — A 방식 / B 방식의 장점·불편한 점·어울리는 상황
5. **내 구현 유지/변경 결정** — "공유회 이후 나는 ___을 변경/유지한다. 이유는 ___이다."

**공유회 산출물**
- 그룹 산출물: 비교한 질문 / A 방식 / B 방식 / 우리 그룹의 결론
- 개인 산출물: 변경/유지 결정 한 줄

### ADR 도입 이유
미션 가이드가 단계마다 "선택 도구 / 다른 후보 / 선택 이유 / 불편한 점"을 PR에 적게 한다. ADR은 **이 양식 그대로**의 의사결정 기록 형식이다. 각 단계의 본문 문서(`02-...`, `03-...`)는 시간순 흐름을 담고, **돌이켜봐도 명확한 결정들**은 `decisions/`에 따로 빼서 공유회 때 한눈에 모이게 한다.

## 7. 각 단계 문서 템플릿

모든 단계 문서(`02-step1-...` 부터)는 다음 골격을 따른다.

**설계 원칙**
- 각 단계마다 **이미 가이드가 명시한 선택 카테고리**(보통 5개)는 **고정 슬롯**으로 미리 비워둔다 → 누락 방지.
- 각 카테고리 안에는 **2~3개 이상의 후보**를 적고, 선택·이유·받아들인 트레이드오프를 표로 정리.
- 구현 중 새로 마주친 **추가 결정들**은 별도 누적 섹션에 ADR ID로 쌓는다 → 결국 한 단계에 10개 안팎의 결정 기록이 자연스럽게 모인다.
- **막혔던 지점 / 인사이트 / 테스트 변경**은 별도 섹션으로 분리 → 결정 기록과 회고 기록이 섞이지 않게.

```markdown
# N단계 — [제목]

> 이 단계의 핵심 질문: ______

- ...

### 구현 조건
- ...
```

### 단계마다 결정이 10개 가까이 쌓이는 이유

가이드가 명시한 카테고리만 1단계에 5개. 그 안에서 구현하다 보면 자연스럽게 갈라진다. 예를 들어 1단계의 경우:

- **3번 섹션(가이드 카테고리):** 5개 슬롯
    1. 로그인 상태 유지 방식 (세션 / 직접 토큰)
    2. 인증이 필요한 API 구분 방식 (경로 / 어노테이션)
    3. 인증 공통 처리 위치 (Interceptor / ArgumentResolver / 조합)
    4. 컨트롤러에 사용자 전달 방식 (세션 직접 조회 / 객체 주입)
    5. 인증 실패 응답 방식 (상태 코드 / 메시지 형식)

- **4번 섹션(구현 중 추가 결정):** 보통 4~6개
    - 비밀번호를 평문으로 받을지, 해시 처리를 어디까지 흉내 낼지
    - `LoginMember` 객체에 어떤 필드를 둘지 (id만 / email까지)
    - 로그인 API 경로 (`/login` / `/auth/login`)
    - 기존 `Reservation.name` 필드를 즉시 제거할지, 유지하며 점진 마이그레이션할지
    - `MyReservationStepTest`의 `?name=` 기반 테스트를 어떤 방향으로 재작성할지
    - 세션 타임아웃을 명시적으로 설정할지

→ **한 단계당 결정 9~11개**가 자연스럽다.
→ 모두 적되, 핵심 결정만 ADR로 따로 분리해 공유회 때 한눈에 모은다.

## 8. 현재 코드 상태 (시작점)

미션 시작 시점의 내 방탈출 예약 서비스 구조.

### 도메인
- `Reservation` — `name(String)`, `date`, `time`, `theme`. **`name`이 사용자 정체성의 기준.**
- `ReservationTime` — `startAt(LocalTime)`
- `Theme` — `name`, `description`, `thumbnailUrl`
- **`Member` 없음** ← 1단계에서 도입
- **`Store`/`Manager` 없음** ← 3단계에서 도입

### 정책
- `ReservationPolicy` (`FutureOnlyPolicy`) — 과거 예약/변경 거부
- `PopularThemePolicy` (`RecentWeekPopularPolicy`) — 인기 테마 집계 기간

→ Policy 패턴이 이미 정착되어 있어, **인가도 같은 패턴(`AccessPolicy` 같은)으로 확장 가능.**

### 컨트롤러
- `AdminReservationController` `/admin/reservations`
- `AdminReservationTimeController` `/admin/times`
- `AdminThemeController` `/admin/themes`
- `UserReservationController` `/user/reservations` ← `?name=` 쿼리로 본인 식별 (1단계에서 변경)
- `UserThemeController` `/user/themes`

→ **인증이 필요한 API와 필요 없는 API의 구분** (1단계 핵심 결정).
대략의 초안:
- 인증 불필요: `POST /login`, `GET /user/themes`, `GET /user/themes/popular`, `GET /user/themes/{id}/available-times`
- 인증 필요: 예약 생성/조회/변경/취소
- 인증 + 권한 필요: `/admin/**` (3단계에서 매장 매니저 권한과 합쳐짐)

### 예외 체계 — 인증/인가에 그대로 활용 가능
```
RoomeScapeException (status 보유)
├── RoomeScapeClientException
│   ├── BusinessRuleViolationException (400)
│   ├── InvalidCommandException (400)
│   ├── ResourceNotFoundException (404)
│   ├── UnauthorizedException (401)        ← 1단계에서 추가
│   └── ForbiddenException (403)           ← 3단계에서 추가
└── RoomeScapeServerException
    └── DataInconsistencyException (500)
```
`GlobalExceptionHandler`가 `RoomeScapeException`을 통합 처리하므로 **새 예외를 추가해도 핸들러 수정 불필요.**

### 테스트 — 일부는 1단계에서 크게 깨질 예정
- `MissionStepTest` — 기존 미션1 검증, 대체로 무사할 듯
- `UserReservationStepTest` — `?name=` 쿼리 안 쓰는 흐름이라 비교적 안전
- `MyReservationStepTest` — **이름 기반 본인 검증을 직접 검증함, 1단계에서 대거 수정 필요**
- `ErrorResponseStepTest` — 일부 응답 메시지 영향
- `ReservationPolicyStepTest` — 정책 단위 테스트, 인증과 직교라 무사
- 도메인 단위 테스트 (`ReservationTest`, `ReservationTimeTest`, `ThemeTest`) — `Reservation.name` 변경 시 영향

### 의존성 미리 본 것
- `build.gradle`에 **JJWT가 이미 들어가 있음**. 토큰 방식 갈 길은 열려 있다 — 단, 사용 여부는 2단계에서 결정.

## 9. 학습할 때 지키고 싶은 원칙

미션 가이드와 공유회 원칙에서 추린 것 + 내 학습 스타일.

1. **동작하면 끝이 아니다.** 각 단계 끝에 반드시 인사이트 한 단락을 docs에 남긴다.
2. **선택하지 않은 길도 적는다.** "왜 안 했는가"는 "왜 했는가"만큼 중요하다.
3. **테스트를 줄이지 않는다.** 깨진 테스트는 고치거나, 의도적으로 옮기거나, 명시적으로 제거한다. 슬쩍 주석 처리 금지.
4. **문서량 자랑 ≠ 학습.** 단계 문서는 30분 안에 정리되는 분량을 유지한다.
5. **모르는 게 있어도 일단 한 가지를 선택하고 구현한다.** 비교는 그 다음에 한다. 가이드가 "정답을 외우지 않는다"고 한 이유다.
