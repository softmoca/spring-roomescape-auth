**인증(Authentication,401 Unauthorized) vs 인가(Authorization,403 Forbidden)**

- 인증은 **요청을 보낸 사용자가 누구인지 확인하는 것**이고,
- 인가는 **그 사용자가 특정 행동을 할 권한이 있는지 확인하는 것**

**Login / Logout**

- **로그인** = 사용자가 자격 증명(email + password)을 제시→ 서버가 검증 → "이 사람 맞다"는 증표를 발급
- **로그아웃** = 그 증표를 무효화
    - **세션이냐 토큰이냐에 따라 난이도가 다르다.**
        - 세션은 서버가 세션을 지우면 끝.
        - 토큰은 서버가 발급 후 잊어버리는 구조라 **"이미 발급한 토큰을 어떻게 무효화하지?"**를 고려해야함

**Cookie**

- 브라우저가 서버로부터 받아서 저장해두고, **같은 서버로 요청할 때마다 `자동`으로 다시 보내주는** 작은 데이터 조각.
- 개발자가 코드로 챙기지 않아도 브라우저가 알아서 붙여준다. 그래서 **웹 브라우저 + 세션 방식**이 편함.
    - 세션 ID를 쿠키에 담아두면 이후 요청에 자동으로 따라옴.
- 반대로 모바일 앱은 브라우저가 아니라서 이 "자동" 혜택이 없거나 어색하다. 그래서 모바일은 헤더 방식이 자연스럽다.

**HTTP Header**

- HTTP 요청/응답에 붙는 메타데이터
    - 인증에서 중요한 건 딱 하나: `Authorization: Bearer eyJhbGc...토큰값`
- **토큰 방식**은 이 `Authorization` 헤더에 토큰을 실어 보냄.
- 쿠키와 달리 자동이 아니라서 클라이언트가 매 요청마다 직접 넣어줘야 한다.
- 번거롭지만 웹/모바일 어디서든 똑같이 동작하는 장점이 있다.
- **쿠키 vs 헤더 한 줄 정리:** 쿠키는 브라우저가 자동으로 챙기는 길, 헤더는 클라이언트가 직접 챙기는 길.

**Session**

- **서버가 로그인 상태(state)를 기억하는** 방식
    - 클라이언트는 보통 `세션 ID`만 가지고 있고,
    - 실제 로그인 정보는 서버 쪽 세션 저장소에 있다.
- 흐름
    1. 로그인 성공
    2. 서버: 세션 저장소에 `"이 세션 ID = 브라운"` 저장
    3. 서버: 세션 ID를 클라이언트에 전달(쿠키에 담아)
    4. 브라우저:  `Set-Cookie` 응답헤더를 보고 세션 ID가 담긴 쿠키를 자동으로 저장
        1. HttpOnly 없음
            1. JS로 쿠키 읽기 가능(document.cookie)
            2. JS로 세션 ID를 직접 확인 가능
            3. XSS에 세션 ID가 털릴 위험 증가
        2. HttpOnly 있음
            1. JS로 쿠키 읽기 불가능
            2. 하지만 브라우저가 요청에는 자동으로 쿠키를 붙여줌
            3. 프론트는 세션 ID 값을 직접 몰라도 로그인된 요청을 보낼 수 있음
    5. 이후 요청마다 클라이언트가 세션 ID를 함께 보냄(브라우자가 자동으로 쿠키를 담아 전달)
    6. 서버: 세션 ID로 세션 저장소를 조회해서 `"아, 브라운이구나"` 식별
- 장점
    - 로그아웃 간단(세션 삭제하면됨)
    - 동시 로그인 제어가 쉽다.(서버가 현재 살아있는 세션들을 모두 앎)
    - 이미 발급한 로그인 상태를 서버가 직접 통제할 수 있다.
- 고민거리
    - 서버가 여러 대가 되면 `"세션을 어디에 저장하지?"` 문제가 생긴다.(세션 저장 위치에 따른 차이)
        - 서버 메모리에 저장
            - 가장 단순하고 빠르다.
            - 하지만 서버가 여러 대면 문제가 생긴다.
            - 예를 들어 로그인 요청은 서버 A로 가서 서버 A 메모리에 세션이 저장됐는데, 다음 요청이 서버 B로 가면 서버 B는 그 세션을 모른다.
        - DB에 저장
            - 여러 서버가 같은 DB를 바라보므로 세션 공유 문제가 해결된다.
            - 어떤 서버로 요청이 가도 DB에서 세션을 조회하면 된다.
            - 다만 로그인 이후 거의 모든 요청마다 세션 조회가 필요하므로 DB 부하가 커질 수 있다.
        - Redis 같은 외부 메모리 저장소에 저장
            - 여러 서버가 함께 바라볼 수 있는 공통 저장소다.
            - DB보다 빠르게 세션을 조회할 수 있어 실무에서 세션 저장소로 자주 사용된다.
            - 즉, 서버 메모리의 빠름과 DB의 공유 가능성을 어느 정도 함께 가져가는 방식이다.
    - 모바일에서는 쿠키 기반 흐름이 웹 브라우저만큼 자연스럽지 않을 수 있다.
        - 모바일에서 세션 쿠키를 쓰려면, 앱의 HTTP 클라이언트가 직접 `Set-Cookie`를 저장하고 이후 요청에 `Cookie` 헤더로 보내도록 해야 한다.
        - 가능은 하지만 웹 브라우저만큼 자연스럽지는 않아서, 모바일 앱에서는 `Authorization` 헤더 기반 토큰 방식이 더 자주 선택된다.

### Token

- **클라이언트가 로그인 증표(상태)를 들고 다니는** 방식
    - 클라이언트가 토큰을 저장하고, 이후 요청마다 토큰을 함께 보낸다.
    - 서버는 "로그인 상태를 기억"하지 않고 매번 토큰을 "검증"만 함( **stateless)**
- 장점 :
    - 서버가 상태를 안 들고 있어서 서버 여러 대로 확장 쉬움
    - 웹/모바일/API 클라이언트 등 다양한 환경에서 같은 방식으로 동작시키기 쉽다.
        - 쿠키 자동 저장/전송 흐름에 의존하지 않고, 토큰을 저장한 뒤 헤더에 직접 넣어 보내면 됨.
- 단점 및 고려할 사항:
    - 로그아웃 처리가 까다롭다.
        - 토큰을 따로 기억하지 않는 구조라면, 이미 발급한 토큰을 즉시 무효화하기 어렵다.
    - 토큰 탈취 대응이 필요하다.
        - 공격자가 토큰을 훔치면, 만료 전까지는 그 토큰으로 요청을 보낼 수 있다. 그래서 토큰 저장 위치와 만료 시간 설계가 중요하다.
        - 예를 들어 localStorage에 저장하면 JS로 접근 가능해서 XSS에 취약할 수 있다.
        - 쿠키에 저장하면 `HttpOnly`, `Secure`, `SameSite` 같은 옵션을 고려해야 한다.
    - 토큰 만료 전략이 필요하다.
        - access token 만료 시간을 너무 길게 잡으면 탈취 시 위험이 커진다.
        - 너무 짧게 잡으면 사용자가 자주 다시 로그인해야 해서 불편하다.
        - 그래서 보통 짧은 access token과 긴 refresh token을 함께 사용하는 구조를 고려한다.
    - refresh token을 쓰면 다시 서버 상태가 필요해질 수 있다.
        - access token은 stateless하게 검증할 수 있지만, 하지만 refresh token을 안전하게 관리하려면 서버에 저장하거나, 재발급 이력을 관리하거나, 탈취 시 무효화할 방법이 필요하다.
        - 이 경우 "토큰은 완전히 stateless하다"기보다는, access token 검증은 stateless하지만 refresh token 관리에는 state가 들어갈 수 있다.
    - 동시 로그인 제어가 세션보다 까다롭다.
        - 토큰 방식은 서버가 발급한 토큰을 기억하지 않으면, 특정 기기의 로그인만 끊는 처리가 어렵다.
        - 동시 로그인 제한, 강제 로그아웃, 특정 토큰 폐기 등을 하려면 블랙리스트나 토큰 저장소 같은 서버 상태가 필요할 수 있다.
- 흐름
    1. 로그인 성공
    2. 서버: 토큰 발급 (사용자 정보(식별자, 권한, 만료기간)가 토큰 안에 들어있음)
    3. 클라이언트: 토큰 저장
        1. 웹  : localStorage, sessionStorage, 메모리, 쿠키 등 선택 가능
        2. 모바일 : 앱 내부 저장소, Secure Storage, Keychain, Keystore 등 사용 가능
    4. 이후 요청마다 클라이언트가 토큰을 함께 보냄 (Authorization 헤더)
    5. 서버: 토큰을 검증해서 사용자 식별(토큰 서명, 만료기간, 권한 등 검증)

**Filter / Interceptor / ArgumentResolver**

- **요청이 컨트롤러에 닿기까지의 경로에 있는 세 가지 "공통 처리" 도구**
- `요청 → [Filter] → DispatcherServlet → [Interceptor] → [ArgumentResolver] → Controller`

- **Interceptor =** **문지기** (요청을 통과시킬지 막을지 결정)
    - 스프링 MVC 안. 컨트롤러 호출 **전/후**에 끼어들어 공통처리를 함.
    - `preHandle()`이 `false`를 리턴하면 컨트롤러로 안 넘어감.
      → **요청을 통과시킬지 막을지 결정**하는 데 적합. = **인증 체크의 자리**.
    - 로그인 없이 접근 가능한 경로들을 제외할 수 있다.
    - 이번 미션에서
        - 이 요청이 로그인 필요한 요청인지 확인한다.
        - 로그인하지 않은 요청을 컨트롤러 전에 차단한다.
        - 특정 경로에 공통 정책을 적용한다.
- **ArgumentResolver = 배달부** (컨트롤러에 현재 사용자 객체를 배달)
    - 컨트롤러 파라미터에 필요한 값을 넣어주는 도구
    - `@LoginMember Member member`라고 쓰면 세션/토큰에서 사용자정보 객체를 꺼내 자동으로 꽂아줌. → **현재 사용자를 컨트롤러에 전달**하는 데 적합.
    - 이번 미션에서
        - 현재 로그인한 사용자를 컨트롤러 파라미터로 전달한다.
        - 세션이나 토큰에서 사용자 정보를 꺼내는 코드를 숨긴다.
        - 컨트롤러가 인증 저장 방식에 덜 의존하게 한다.
    - 주요 코드 설명
        - boolean supportsParameter(MethodParameter parameter)
          → 이 ArgumentResolver가 어떤 파라미터를 처리할지 결정
            - parameter.hasParameterAnnotation(LoginMember.class)
                - `@LoginMember` 가 있는지 확인
            - Member.class.isAssignableFrom(parameter.getParameterType())
                - 파라미터 타입이 Member인지 확인
        - resolveArgument(...) - 실제로 컨트롤러 파라미터에 넣어줄 값을 만듬
            - session.getAttribute("loginMemberId")
                - 세션에서 로그인 사용자 ID를 꺼냄.

### 이번 미션에서 생각할점

1. 이름 기반 식별이 위험한 이유는?
    1. 이름 기반 식별의 위험은 이름이 누구나 자유롭게 입력할 수 있는 값이라, 서버가 "주장하는 사람"과 "실제 그 사람"을 구분하지 못한다 는 것이다.이름은 주장일 뿐, 증명이 아니다. 남의 이름으로 요청하면 조작할수 있다.
2. Interceptor를 사용하면 어떤 코드 반복이 줄어드나요?
    1. → 컨트롤러마다 쓰던 `if (loginMember == null) throw ...` 인증 체크가 한 곳으로 모임.
3. 모든 `/reservations/**` 경로에 인증이 필요할까요?
    1. 아니요. 인기 테마 조회처럼 비로그인 허용이 자연스러운 게 있음. `excludePathPatterns`로 제외.
4. 관리자 API와 사용자 API는 같은 Interceptor를 써도 될까요?
    1. → 인증(로그인 여부)은 같이 써도 됨. **하지만 인가(관리자냐)는 판단 기준이 달라서 분리 고민 필요.**
5. 인증 실패 응답 본문을 내려주려면 어떻게 바꿔야 할까요?
    1. 보통 Interceptor에서 먼저 막음. ArgumentResolver는 "이미 통과한 요청"을 가정.
    2. 단 ArgumentResolver에서도 방어적으로 한 번 더 던질 수 있음(샘플 코드가 그렇게 되어 있음).
        1. if (session == null) {  throw new UnauthorizedException();  }

- **[1] 로그인이 필요한 API와 필요하지 않은 API는 어떻게 구분할 수 있을까요?**
  예시:로그인, 로그아웃, 인기테마 조회, 예약 생성, 내 예약 조회, 매장 예약 관리, 관리자 기능
    - 표면적으로는 "**API에 인증 도장을 찍을지 말지**" 분류 문제처럼 보이지만,
      **"인증의 기본값을 무엇으로 둘 것인가**"라는 설계 철학 질문.

  | API | 로그인 필요? | 이유 |
      | --- | --- | --- |
  | 로그인 (`POST /login`) | ❌ | 인증의 입구는 밖에 있어야함 |
  | 로그아웃 (`POST /logout`) | △ | 애매함 - 고민과 선택 |
  | 인기 테마 조회 
    (`GET /user/themes/popular`) | ❌ | 누구나 보는 공개 정보.  |
  | 예약 생성 (`POST /user/reservations`) | ✅ | "누가 예약했는가"가 데이터의 일부. 
    로그인한 사람이 곧 예약 소유자 |
  | 내 예약 조회 (`GET /user/reservations`) | ✅ | "내"가 누군지 모르면 응답 불가능 |
  | 매장 예약 관리 | ✅ + 인가 | 로그인만으론 부족. 
    "이 매장 매니저인가"까지 봐야 함 |
  | 관리자 기능 (`/admin/**`) | ✅ + 인가 | 로그인 + "관리자 역할인가" |

  **`인사이트 1` - 인증 필요 여부는 사실 3단계(비로그인 혀용, 로그인만 필요, 로그인 +인가)**

    - **2단계와 3단계는 처리 위치가 다르다.**
    - 2단계(로그인 여부)는 데이터를 안 봐도 판단가능 - "세션에 사용자 있나?"만 보면 끝. 그래서 Interceptor에서 처리 가능.
    - 반면 3단계(이 매장 매니저인가)는 어떤 예약인지 데이터를 봐야 판단가능.
    - Interceptor 시점엔 아직 그 정보가 없다.
    - 이건 질문 4에서 깊게 다룰 주제인데, **질문 1의 분류가 이미 "어디서 처리할지"를 결정하고 있다.**

  **`인사이트 2`**- 분류기준

    - 로그인이 필요한 API의 공통점”**요청을 처리하려면 "이 요청이 누구 것인지" 알아야 하는가?”
      "요청자가 누구인지에 따라 응답이 달라지면, 그 식별은 서버가 책임진다(=인증 필요)."**
        - 예약 생성 → "누가 예약했는지"가 저장돼야 함 → **필요**
        - 내 예약 조회 → "내"를 특정해야 함 → **필요**
        - 인기 테마 조회 → 응답이 요청자와 무관, 누가 봐도 같은 결과 → **불필요**
    - 다른 기준
        - **데이터를 바꾸는가?**
            - 생성·변경·삭제(POST/PATCH/DELETE)는 책임 소재가 남아야 하므로 인증이 필요한 경우가 많음. 단순 공개 조회(GET)는 아닌 경우가 많음. (절대 규칙은 아님 - "내 예약 조회"는 GET이지만 인증 필요)
        - **응답이 사람마다 다른가?**
            - 인기 테마는 모두에게 같음(불필요), 내 예약은 사람마다 다름(필요)

  **`인사이트 3`** - 로그아웃

    - **"로그인 안 했어도 로그아웃 호출 가능해야지"** → 비로그인 허용. 이미 만료된 세션으로 로그아웃을 또 눌러도 그냥 조용히 성공 처리하면 됨 (멱등성)
    - **"로그아웃은 로그인한 사람만 하는 행위지"** → 로그인 필요

  정답은 없지만 **실용적으로는 비로그인 허용 쪽이 깔끔하다.**

  로그아웃은 "상태를 없애는" 행위인데, 없앨 게 없는 상태에서 호출돼도 결과는 똑같이 "로그아웃상태"면된다. 굳이 401로 막으면 사용자 입장에선 "로그아웃하려는데 로그인하라고?"라는 이상한 경험이 된다.

  **`인사이트 4`** - 가장 중요한 것: "기본값을 무엇으로 둘 것인가" -

  API를 분류하는 방식에는 두 가지 정반대 철학이 있다.

  **A. 화이트리스트 (기본 차단)** - "모든 API는 인증 필요. 단, 명시적으로 허용한 것만 열어준다."

    - `.addPathPatterns("/**")                    // 전부 막고`
    - `.excludePathPatterns("/login", "/themes/popular")  // 예외만 연다`

  **B. 블랙리스트 (기본 허용)** — "모든 API는 공개. 단, 명시적으로 지정한 것만 막는다."

    - `.addPathPatterns("/user/reservations/**", "/admin/**")  // 막을 것만 지정`

  **보안에서는 A(화이트리스트)가 정석**

    - 새로운 `POST /user/reviews`(후기 작성)를 만들경우
    - **A 방식**: 깜빡하고 인증 설정을 안 하면 → 기본이 "차단"이라 → 후기 작성이 막힘 → 개발 중 바로 발견 → 고침. **실수가 안전한 방향으로 터짐**
    - **B 방식**: 깜빡하면 → 기본이 "허용"이라 → 인증 없이 누구나 후기를 쓸 수 있음 → **아무도 모름** → 운영에 보안 구멍이 그대로 나감.

  보안 원칙 **Secure by default** 또는 **Fail-safe default**라고부름.

    - 실수했을 때 안전한 쪽으로 실패하게 설계한다.
    - 사람은 반드시 깜빡하므로, 깜빡했을 때 뚫리는 게 아니라 막히도록 만드는게 좋다.
    - 질문 2가"**API가 많아져도 유지보수하기 쉬울까요?**"라고 물었던 게 바로 이 지점을 말함.

- **[2] Interceptor에서 인증을 확인한다면, 경로 패턴을 어떻게 관리할 수 있을까요?
  이 방식이 API가 많아져도 유지보수 하기 쉬울까요 ?**

  ex).addPathPatterns("/reservations/**") .excludePathPatterns("/login", "/themes/popular")

  **위 예시는 시간이 지나면 무너진다.**

  **`인사이트 1`** -  경로 패턴 방식이 무너지는 3가지 시나리오

  **시나리오 A - 새 API 추가 시 깜빡한다**

    - 질문 1에서 말한 **"기본값 차단"이 이 코드에선 안 지켜짐.**
    - `addPathPatterns`로 *막을 것을 일일이 지정*하는 건 사실상 블랙리스트.
    - 깜빡하면 안전한 쪽이 아니라 **뚫리는 쪽으로 실패**.

  **시나리오 B -  공개 API가 늘어날때 마다 exclude 목록이 계속 길어진다**

    - 어떤 게 "의도적으로 공개"고 어떤 게 "그냥 빠진 것"인지 구분이 안 됨.(설계의도를 못읽음)

  **시나리오 C - 패턴 충돌이 점차 발생**

    - `/admin/**`은 인증 필요, 그런데 `/admin/health`(헬스 체크)는 공개하고 싶다.
    - 패턴이 겹치기 시작하면 어느 규칙이 이기는지 헷갈리고, URL을 살짝만 바꿔도(`/reservations` vs `/reservation`) 패턴이 빗나가 인증이 통째로 새어나감.
    - **패턴 매칭은 컴파일러가 검증 안함** → 오타가 나도 빌드는 통과하고, 런타임에 조용히 뚫림

  `인사이트 2` - 문제의 본질: "인증 정보가 코드에서 멀리 떨어져 있다"

  > **"이 API가 인증이 필요한가"라는 정보가, 그 API를 정의하는 컨트롤러가 아니라 저 멀리 Config 파일의 문자열 목록에 적혀 있다.**
  >
    - 개발자는 `ReviewController`를 만들면서 작업함. 그런데 인증 설정은 `AuthConfig`에 있다.
      **물리적으로 떨어져 있으니 같이 수정하는 걸 잊는다다.** 이게 시나리오 A의 진짜 원인.
    - 좋은 설계는 **"같이 바뀌어야 하는 것을 가까이 둔다"**(응집도). API의 인증 요구사항은 그 API 옆에 있어야 함.

  **`관리 방식 3가지  단계별로 비교`**

  **방식 1 - 경로 패턴 (가이드 기본형)**

    - 👍 처음엔 간단, 한눈에 보임. API 5~10개 규모에선 충분.
    - 👎 위 세 시나리오. 깜빡하면 뚫림.

  **방식 2 — 화이트리스트 뒤집기 (전부 막고 예외만 연다)**

    - 👍 **기본값이 차단.** 새 API를 깜빡하면 → 막힘 → 개발 중 바로 발견. 시나리오 A 해결.
    - 👎 정적 리소스(css/js/이미지)까지 다 막혀서 exclude 목록에 그것들도 들어감. 그래도 방식 1보다 안전한 방향.

  **방식 3 - 애노테이션 기반 (인증 정보를 API 옆으로)**

    - 경로 문자열 대신, 컨트롤러 메서드에 마크를 담.

    ```java
    @PostMapping("/user/reservations")
    public ReservationResponse create(@LoginMember Member member, ...) { }
    // → @LoginMember 파라미터가 있으니 "이 API는 인증 필요"가 자명
    
    // 또는 명시적 애노테이션
    @LoginRequired
    @PostMapping("/user/reviews")
    public ReviewResponse create(...) { }
    ```

    - Interceptor는 경로를 매칭하는 대신, **호출될 핸들러(컨트롤러 메서드)에 그 마크가 있는지** 검사함

    ```java
    public boolean preHandle(..., Object handler) {
        if (!(handler instanceof HandlerMethod handlerMethod)) return true;
        boolean needsLogin = handlerMethod.hasMethodAnnotation(LoginRequired.class);
        if (needsLogin && 세션없음) { response.setStatus(401); return false; }
        return true;
    }
    ```

    - 👍 인증 요구사항이 **API 정의 바로 옆에** 있음. 컨트롤러를 만들면서 자연스럽게 같이 작성 → 깜빡할 일이 줄어듦. 시나리오 A·B·C 모두 완화.
    - 👎 모든 컨트롤러 메서드에 애노테이션을 일일이 달아야 함. 빠뜨리면 또 뚫림(방식 2와 비슷한 한계).

  > `preHandle`의 세 번째 파라미터 `Object handler`가 바로 이걸 위해 있다. 가이드 코드 샘플엔 안 쓰이지만, 이 파라미터를 `HandlerMethod`로 캐스팅하면 "어떤 컨트롤러 메서드가 호출될 예정인지"와 거기 붙은 애노테이션을 다 알 수 있다.
>

- **[3] ArgumentResolver에서 현재 사용자를 조회한다면, 인증 실패는 어디에서 처리해야 할까요?**
  **인증 실패라는 책임은 둘중 누가 지는가?**

  **선택지 A - Interceptor에서 먼저 막는다 (ArgumentResolver는 검사 안 함)**

    ```java
    // Interceptor: 세션 없으면 401, return false
    // ArgumentResolver: 세션이 있다고 "믿고" 그냥 꺼냄
    Long memberId = (Long) session.getAttribute(LOGIN_MEMBER_ID);
    return memberRepository.findById(memberId).get();  // 검사 없음
    ```

    - 논리: "Interceptor를 통과했다는 건 이미 로그인했다는 뜻. 아규먼트리졸버가 또 검사하면 중복."
    - 문제: **ArgumentResolver가 Interceptor에 "암묵적으로 의존"함.**
        - 누군가 Interceptor의 `addPathPatterns`에서 그 경로를 빼먹으면 → ArgumentResolver는 세션이 없는데도 있다고 믿고 → `session.getAttribute`가 `null` 반환 → `findById(null)` → **`NullPointerException` → 500 에러**. 사용자에게 깔끔한 401이 아니라 서버 에러가 노출됌.
    - 즉, "Interceptor 설정이 항상 완벽하다"는 가정 위에서만 안전함

  **선택지 B - ArgumentResolver에서만 예외를 던진다 (Interceptor 없음)**

    - ArgumentResolver가 세션 검사 + 예외 던지기 다 함
    - 논리: "어차피 ArgumentResolver가 사용자를 꺼낼 때 세션을 보니까, 거기서 검사하면 Interceptor가 필요 없다."
    - 문제 1: **`@LoginMember` 파라미터가 없는 API는 검사가 아예 안 됨.**
        - 예를 들어 `DELETE /user/reservations/{id}`를 만들 때 컨트롤러가 `@LoginMember`를 안 받고 다른 방식으로 짜였다면 → ArgumentResolver가 호출조차 안 됨 → 인증이 통째로 새어나감.
    - 문제 2: **차단 시점이 늦음.**
        - ArgumentResolver는 컨트롤러 메서드를 *호출하기 직전*에 동작함. 인증은 가능한 한 일찍 막는 게 좋음(불필요한 처리를 줄이고, 차단 책임을 한 곳에 모음)
    - B는 ArgumentResolver의 역할을 넘어선 사용 - 배달부에게 문지기 일까지 시킴

  **선택지 C — 둘 다 처리한다 (가이드 샘플 코드의 방식)**

    ```java
    // Interceptor: 1차 방어 — 로그인 안 했으면 여기서 막음
    // ArgumentResolver: 2차 방어 — 세션/사용자 없으면 또 던짐
    ```

    - 논리: "Interceptor가 메인 방어선, ArgumentResolver는 안전망."
    - "중복 아닌가?"라는 의심이 들지만, **이건 의도된 중복임**.다층 방어(defense in depth)원칙. 한 겹이 뚫려도 다음 겹이 잡음.
    - 구체적으로: Interceptor 설정에서 경로를 빼먹어도(시나리오 A) → ArgumentResolver가 `memberId == null`을 잡아 `UnauthorizedException`을 던짐 → A처럼 NPE 500이 나는 게 아니라 **깔끔한 401**이 나감.
    - 비용: 같은 검사 코드가 두 곳에 있음. 하지만 인증 검사는 가볍고(세션 조회 한 번), 그 비용보다 "한 겹이 뚫려도 안전"이 훨씬 큽큼.

  **선택지 D - 다른 방식**

    - 예: 인증 로직을 `AuthService` 같은 공통 서비스로 빼고, Interceptor와 ArgumentResolver가 둘 다 그 서비스를 호출. → 검사 *코드*는 한 곳(중복 제거), 검사 *시점*은 두 곳(다층 방어 유지). C의 장점은 살리고 중복은 줄이는 절충안.
    - 미션 가이드가 D를 열어둔 건 "C가 정답"이라고 외우지 말라는 뜻.

  **`인사이트 1`** - "역할이 다르면 책임도 다르다"

  Interceptor와 ArgumentResolver는 **인증 실패에 대해 서로 다른 책임**을 짐

  |  | Interceptor | ArgumentResolver |
      | --- | --- | --- |
  | 던지는 질문 | "들여보낼까 말까?" | "이 파라미터를 채울 수 있나?" |
  | 인증 실패의 의미 | "이 요청은 막아야 한다" | "줄 사용자가 없다 → 작업 불가" |
  | 실패 처리 성격 | **1차 방어** (메인) | **안전망** (보조) |
    - 같은 `UnauthorizedException`을 던지지만 *맥락*이 다름.
    - Interceptor는 "정책상 차단", ArgumentResolver는 "기술상 값을 못 만듦".
    - 그래서 C(둘 다)가 중복이 아니라 **역할에 충실한 결과** 임

  **`인사이트 2`** - 미션 2의 예외 계층과 **Interceptor 쪽 주의 사항**

    - 가이드의 Interceptor 샘플은 `response.setStatus(401); return false;`로 끝남.
    - 이건 **예외를 던지는 게 아니라** 상태 코드만 찍고 끝낸 거라, `@ExceptionHandler`를 *거치지 않아서 응답 본문이 비어버림.(에러이유 없이 상태 코드만 반환- 규칙 위반)*
    - 5번 - *"인증 실패 응답 본문을 내려주려면 어떻게 바꿔야 하나요?"* 가 바로 이걸 묻는것.
    - 답은: Interceptor에서도 `setStatus + return false` 대신 **예외를 던짐**(`HandlerExceptionResolver`를 통해 핸들러로 연결)

  **`인사이트 3`** - 선택과 그 이유

  이 미션에서 권하는 선택은 **C (둘 다)**. 단, D의 정신을 약간 섞어서.

    - **Interceptor**: 1차 방어. 인증 필요한 경로에서 로그인 여부 확인. 실패 시 **본문까지 챙긴 401**(위 함정 해결).
    - **ArgumentResolver**: 안전망. `@LoginMember`를 resolve할 때 세션/사용자가 없으면 `UnauthorizedException`. Interceptor가 빠뜨린 경로를 잡아 **NPE 500 대신 깔끔한 401**.
    - (선택) 두 곳의 검사 *코드*가 진짜 똑같아 신경 쓰이면, `AuthService.getLoginMemberId(request)` 같은 메서드로 빼서 양쪽이 호출 → 코드 중복은 제거, 검사 시점 이중화는 유지.

  **한 줄 이유:** Interceptor 설정은 사람이 관리하는 문자열 목록이라 언젠가 깨진다(질문 2). 그 가정 위에서 ArgumentResolver가 검사를 생략하면(선택지 A) 깨졌을 때 500이 난다. 둘 다 검사하면 한 겹이 뚫려도 사용자에겐 항상 의도된 401이 간다.


- **[4] 매장 매니저가 자기 매장 예약만 관리할 수 있는지는 어디에서 확인해야 할까요?**
  **인증과 인가는 같은 위치에서 처리해야 할까요? 아니면 다르게 처리해야 할까요?**
  Interceptor,ArgumentResolver,Controller,Service,Repository

  **`인가 요구사항을 쪼개기` -**"각 매장 매니저는 자기 매장 예약만 관리할 수 있다"

    1. 현재 사용자가 **로그인했는가?** ← 인증
    2. 현재 사용자가 **매장 매니저인가?** (역할 확인)
    3. 현재 사용자가 **이 매장의** 매니저인가? (소속 확인)
    4. 현재 사용자가 **이 예약을** 관리할 권한이 있는가?

  **1번은 데이터를 안 봐도 판단되지만, 3,4번은 데이터를 봐야 판단됨.**

    - 1번 "로그인했나?" → 세션에 사용자가 있나만 보면 끝. 어떤 예약인지 몰라도 됨.
    - 2번은 “역할 기반 인가”라서 세션/토큰에 role이 있으면 Interceptor에서도 처리할 수 있다.
    - 3번 "이 매장의 매니저인가?" → 먼저 그 예약이 어느 매장 건지 `DB`에서 조회해야 함. 그래야 매니저의 매장과 비교 가능.

  이 차이가 "어디서 처리하나"의 답을 통째로 결정함.

  **`인사이트 1`** - 인가가 인증과 결정적으로 다른 점: "맥락이 필요하다"

    - 인증은 **요청자만** 보면 됨. "이 사람 로그인했나?" 요청자 정보만으로 완결.
    - 인가는 **요청자 + 대상**을 같이 봐야 함. "이 매니저가 이 예약을 관리해도 되나?"
      요청자(매니저)와 대상(예약)을 둘 다 알아야, 그리고 둘을 비교해야 판단됨
        - 그래서 인가는 “대상 데이터를 가진 시점”에서만 처리할 수 있다.

    ```java
    인증:  요청자  →  판단 가능
    인가:  요청자 + 대상 → 비교 → 판단 가능
                  ↑
            이 대상 정보를 어디서 얻나? = DB 조회 필요
    ```

  ### 선택지 5개를 제약 조건에 비춰 검증

  **Interceptor - ❌ (부분적으로만 가능)**

    - 이 시점에 가진 정보는 URL과 헤더뿐 - **`reservationId`가 어느 매장 건지 아직 모름.**
    - "이 사용자가 매니저 역할인가?"(2번)까지는 Interceptor에서 됨. 역할은 사용자 정보에 박혀 있으니까. `/admin/**` 경로를 매니저/관리자만 통과시키는 정도.
    - 하지만 "이 예약이 그의 매장 건가?"(3,4번)는 불가능. 예약을 조회해봐야 알고, Interceptor는 그걸 안 함.
    - → Interceptor는 **거친 인가**(역할 기반, 경로 기반)까지만. **세밀한 인가**(이 리소스가 네 것인가)는 못 함.

  **ArgumentResolver - ❌**

    - ArgumentResolver의 역할은 "파라미터 채우기”.
    - `@LoginMember Member member`에 현재 사용자를 꽂아주는 것까지가 일.
    - 여기서 인가 판단까지 하면 **배달부가 심사관 일을 겸하는** 격 → 역할이 오염됨
        - 게다가 ArgumentResolver도 아직 예약 데이터를 모름.

  **Controller — △ (가능하지만 부적절)**

    - `reservationId`를 path로 받았으니, 예약을 조회해 매장을 비교할 수 있지만
    - 컨트롤러의 책임은 "웹 요청/응단”. 인가는 비즈니스 규칙이지 웹 처리가 아님.
    - 결정적 문제: **인가를 컨트롤러에 두면, 컨트롤러를 거치지 않는 경로에서 인가가 빠짐.**
        - 예를 들어 다른 서비스 메서드가 같은 예약 삭제 로직을 재사용하면? 컨트롤러의 인가 검사를 건너뜀.  콘솔 UI 같은 "다른 입구"가 생기면 그대로 뚫림

  **Service - ✅ (핵심 인가의 자리)**

    - Service는 비즈니스 플로우를 담당하며, 인가는 **비즈니스 규칙**이다
        - "남의 매장 예약은 못 건드린다"는 도메인 규칙이지 웹 기술이 아님.

    ```java
    public void deleteByManager(Long reservationId, Member manager) {
        Reservation reservation = reservationRepository.findById(reservationId)
                .orElseThrow(() -> new ResourceNotFoundException("존재하지 않는 예약입니다."));
    
        // ★ 인가 검사 — 대상을 손에 쥔 직후
        if (!reservation.getTheme().getStoreId().equals(manager.getStoreId())) {
            throw new ForbiddenException("다른 매장의 예약은 관리할 수 없습니다.");
        }
    
        reservationRepository.deleteById(reservationId);
    }
    ```

  왜 Service가 맞나:

    - **대상 데이터를 쥔 시점이다.** `findById`로 예약을 막 조회했으니, 매장 비교에 필요한 정보가 다 손에 있음.
    - **입구가 달라도 보호된다.** 웹이든 콘솔이든 다른 서비스든, 이 메서드를 거치는 한 인가 검사를 통과해야 함. 컨트롤러 방식의 구멍이 막힘.
    - **이미 나의 코드에 선례가 있다.** 미션 2의 `findByIdAndName`이 사실상 인가임.
      `.filter(r -> r.getName().equals(name))`은 "이 예약이 네 것인가"를 Service에서 검사한 것. 이름 비교를 매장/소유자 비교로 바꾸기만 하면 됨. 자리는 이미 옳았음.

  **Repository - ❌**

    - Repository의 책임은 DB 접근입
    - "권한이 없으면 거부한다"는 비즈니스 판단을 여기 넣으면 계층 책임이 깨짐.
    - 단, 기술적으로는 쿼리에 조건을 섞을 수 있긴 함 - `WHERE store_id = ?`로 애초에 남의 매장 예약은 조회조차 안 되게. 이건 성능상 유용한 보조 기법이지만, **인가의 "주" 위치는 아님.** 보조 방어선 정도로만.

  **`인사이트 2`**  "인증과 인가는 같은 위치인가?"

  > **아니다. 다른 위치에서 처리한다. 그 이유는 둘이 필요로 하는 정보가 다르기 때문이다.**
  >

    ```java
    인증(로그인했나?)      → Interceptor   — 요청자만 보면 됨, 일찍 막을 수 있음
    거친 인가(역할이 맞나?) → Interceptor   — 역할은 사용자 정보에 있음
    세밀한 인가(이 리소스가 네것인가 ? → Service   — 대상 데이터를 봐야 함, 비즈니스 규칙)
    ```

  핵심 원리 한 줄: **"판단에 필요한 정보가 모이는 가장 이른 지점에서 처리한다."**

    - 인증에 필요한 정보(요청자)는 요청 진입 시점에 다 있음 → 가장 이른 곳, Interceptor.
    - 세밀한 인가에 필요한 정보(대상 리소스)는 DB 조회 후에야 생김 → 그게 가능한 가장 이른 곳, Service.
    - 질문 3에서 본 "역할이 다르면 책임도 다르다"의 연장. 인증과 인가는 다른 질문이고, 다른 정보를 필요로 하며, 그래서 다른 위치임.

  **`인사이트 3`** - 그래서 인가는 "한 곳"이 아니라 "여러 겹"이다

    - 인가는 단일 지점이 아니라 **계층마다 다른 입자 크기로** 존재함.

    ```java
    Interceptor : "로그인 안 했거나 매니저도 아니면 → /admin/** 진입 자체를 차단"(거친 체)
                                    ↓ 통과
    Service     : "이 예약, 네 매장 것 맞아? 아니면 → ForbiddenException" (고운 체)
                                    ↓ (선택)
    Repository  : "쿼리에 store_id 조건 — 남의 매장은 조회조차 안 됨"   (보조)
    ```

    - 질문 3에서 본 다층 방어(defense in depth)가 인가에서도 똑같이 적용됨.
        - Interceptor가 거친 체로 명백한 경우를 거르고(비매니저는 아예 진입 차단 → 불필요한 DB 조회 절약), Service가 고운 체로 "이 리소스가 네 것인가"를 정밀하게 판단함.
    - **단, "주 방어선은 Service"라는 건 분명함.** Interceptor 인가는 최적화이자 보조일뿐.
        - 만약 Interceptor 인가를 깜빡 빠뜨려도 Service가 잡아주면 시스템은 여전히 안전함. 반대로 Service 인가를 빠뜨리면 - Interceptor의 거친 체로는 "이 예약이 네 것인가"를 거를 수 없으므로 - 매니저 A가 매니저 B의 매장 예약을 삭제할 수 있게 됨. **빠뜨렸을 때 치명적인 쪽이 주 방어선.**

  **`인사이트 4`** - 403이냐 404냐, 그리고 미션 2와의 일관성

  Service에서 세밀한 인가를 검사하다가 실패했을 때, 어떤 예외를 던질지 선택해야 한다.

    ```java
    // 선택 A — 403 "리소스는 존재하지만, 너에게는 관리 권한이 없다."
    throw new ForbiddenException("다른 매장의 예약은 관리할 수 없습니다.");
    
    // 선택 B — 404  "너에게는 없는 리소스처럼 다룬다."
    throw new ResourceNotFoundException("존재하지 않는 예약입니다.");
    ```

  둘 다 방어 가능한 선택이다.

    - **403 Forbidden**
        - 리소스는 존재한다.
        - 하지만 현재 사용자에게 그 리소스를 다룰 권한이 없다.
        - 권한 없음이라는 피드백이 명확하다.
    - **404 Not Found**
        - 현재 사용자에게는 없는 리소스처럼 다룬다.
        - 리소스 존재 여부를 숨길 수 있다.
        - 정보 노출을 줄이는 데 유리하다.

    - 미션 2에서는 일반 사용자가 다른 사람의 예약을 취소하려고 할 때 `404 Not Found`를 선택했다.
        - 왜냐하면  일반 사용자에게 남의 예약 존재 여부를 알려줄 필요가 없다.
        - “권한이 없습니다”라고 알려주면, 해당 예약 ID가 실제로 존재한다는 힌트를 줄 수 있다.
          그래서 일반 사용자 영역에서는 404가 자연스럽다.
    - 하지만 매장 매니저 영역은 성격이 조금 다르다.
        - 매니저는 일반 사용자가 아니라, 예약 관리 권한을 일부 가진 내부 운영자다.
        - 따라서 다른 매장의 예약을 관리하려고 했을 때, “존재하지 않는 예약입니다.” 보다 “다른 매장의 예약은 관리할 수 없습니다.”가 더 명확한 피드백일 수 있다.

  일반 사용자 영역

    - 다른 사용자의 리소스 접근 시 404
    - 이유: 리소스 존재 여부를 숨기는 것이 더 중요함

  매니저/관리자 영역

    - 존재하지만 관리 권한이 없는 리소스 접근 시 403
    - 이유: 내부 운영자에게는 "권한 없음"이라는 명확한 피드백이 더 중요함


- **[5] 웹 인증을 모바일 앱 요청으로 확장할 때, Interceptor와 ArgumentResolver는 그대로 사용할 수 있을까요? 웹에서는 세션 쿠키를 사용한다. 모바일 앱에서는 Authorization Header를 사용한다.
  이때 현재 로그인 사용자를 찾는 코드는 어떻게 달라질까요?**
    - 이 질문은 미션 2단계의 핵심이다.
    - 그리고 앞서 "세션으로 시작하자"고 정한 결정이 실제로 어떤 작업을 만드는지를 보여주는 질문이기도 하다. 가이드의 마지막 물음 — "현재 로그인 사용자를 찾는 코드는 어떻게 달라질까?" — 를 정면으로 품

  **먼저 무엇이 같고 무엇이 다른지 정확히 그리기**

    - 웹과 모바일은 둘 다 HTTP 요청을 보낸다. **다른 건 딱 하나, 인증 정보를 어디에 싣느냐.**
        - 웹 브라우저:  요청 → 쿠키에 세션 ID         (브라우저가 자동 첨부)
        - 모바일 앱:    요청 → Authorization 헤더에 토큰  (앱이 직접 첨부)

  이 차이가 코드의 어디까지 번지는지를 추적하는 게 질문 5이다.

  결론적으로 **번지는 범위는 생각보다 좁다.** 그리고 그 "좁음"이 핵심 인사이트이다.

  **`인사이트1`**  - 코드를 세 층으로 나눠보면, 바뀌는 건 한 층뿐

    - [A] 인증 정보를 꺼내는 층    : 쿠키/세션에서? 헤더에서?       ← 여기만 바뀜
      [B] 사용자를 식별하는 층      : 꺼낸 값으로 누구인지 알아냄
      [C] 그 사용자를 쓰는 층       : 컨트롤러, 인가, 비즈니스 로직
    - 웹→모바일 확장에서 **바뀌는 건 오직 [A]뿐,** [B]와 [C]는 그대로임.
    - 왜냐하면 [A]가 하는 일은 "요청에서 날것의 인증 값을 뽑아 → 누구인지로 바꾸는 것"인데, 일단 "누구인지"(`memberId` 또는 `Member`)가 손에 들어오면 그 다음부터는 웹이든 모바일이든 **완전히 동일**하기 때문이다. 컨트롤러는 `member.getId()`를 쓸 뿐, 그 member가 쿠키에서 왔는지 헤더에서 왔는지 알 필요도, 알 이유도 없다.
    - "현재 로그인 사용자를 찾는 코드는 어떻게 달라지나?" → **"찾아내기까지의 코드([A])만 달라지고, 찾아낸 다음([B][C])은 안 달라진다."**

  **`인사이트 2` - 그래서 Interceptor·ArgumentResolver는 "그대로 쓸 수 있다", 단 조건부**

  > **구조는 그대로 쓸 수 있다. Interceptor와 ArgumentResolver라는 틀, 등록 방식, 컨트롤러 시그니처는 전혀 안 바뀐다. 바뀌는 건 그 안에서 "인증 정보를 꺼내는 줄"뿐이다.**
  >

    ```java
    // LoginCheckInterceptor — 웹 전용
    HttpSession session = request.getSession(false);
    if (session == null || session.getAttribute(LOGIN_MEMBER_ID) == null) { ... }
    
    // LoginMemberArgumentResolver — 웹 전용
    HttpSession session = request.getSession(false);
    Long memberId = (Long) session.getAttribute(LOGIN_MEMBER_ID);
    ```

    - 여기서 `request.getSession()...`이 [A]이다.
    - 모바일을 받으려면 이 줄이 "쿠키 세션도 보고, 없으면 Authorization 헤더도 본다"로 바뀐다. **나머지는 한 줄도 안 바뀜.** `preHandle`이 `boolean`을 리턴하는 것도, `@LoginMember Member`로 받는 컨트롤러도, 그 뒤 인가·서비스 로직도 전부 그대로.
    - → Interceptor·ArgumentResolver를 "도구"로 쓴 게 여기서 보상받음.
    - 만약 인증 정보 꺼내는 코드가 컨트롤러마다 흩어져 있었다면, 모바일 확장 때 **그 모든 컨트롤러를 다 고쳐야** 했을 것임. 공통 처리로 분리해뒀기 때문에 **고칠 곳이 [A] 한 군데로 모임.**
    - 미션 학습 평가 1번 - "인증/인가 로직이 컨트롤러 밖 공통 처리로 분리되었는가" — 의 진짜 효용이 이 순간 드러남

  **`인사이트 3`** - 핵심 설계 결정: [A]를 어떻게 추상화할 것인가

    - [A]가 바뀐다는 건 알았는데, **어떻게 바꾸느냐**에 두 가지 방식이 있다.

  **방식 1 — if 분기 (소박한 방식)**

    ```java
    // ArgumentResolver 안에서
    String token = request.getHeader("Authorization");
    if (token != null) {
        memberId = 토큰에서_추출(token);          // 모바일
    } else {
        HttpSession session = request.getSession(false);
        memberId = (Long) session.getAttribute(LOGIN_MEMBER_ID);  // 웹
    }
    ```

    - 동작은 하며, 미션 통과도 가능하다.
    - 문제: 인증 방식이 또 늘면(예: API 키) `if`가 또 붙고, 같은 분기가 Interceptor에도, ArgumentResolver에도 **중복**됨. 질문 2에서 본 "패턴이 흩어지면 무너진다"와 같은 냄새.

  **방식 2 — 인증 추출을 인터페이스로 분리 (확장에 열린 방식)**

    - "요청에서 사용자를 식별한다"는 책임 자체를 하나의 인터페이스로 뽑음

    ```java
    public interface AuthenticationExtractor {
        boolean supports(HttpServletRequest request);   // 내가 처리할 요청인가?
        Long extractMemberId(HttpServletRequest request); // 사용자 식별
    }
    
    // 구현체 1 — 웹
    class SessionAuthenticationExtractor implements AuthenticationExtractor { ... }
    // 구현체 2 — 모바일
    class TokenAuthenticationExtractor implements AuthenticationExtractor { ... }
    ```

  Interceptor와 ArgumentResolver는 어느 방식인지 모른 채 "사용자 식별해줘"라고 위임만 함.

    ```java
    // 어느 추출기든 처리 가능한 놈이 처리
    Long memberId = extractors.stream()
            .filter(e -> e.supports(request))
            .findFirst()
            .map(e -> e.extractMemberId(request))
            .orElseThrow(UnauthorizedException::new);
    ```

    - 새 인증 방식이 생기면 → **구현체 하나만 추가.** Interceptor·ArgumentResolver는 손도 안 댐.(OCP)
    - **어느 쪽을 쓰나?** 미션 규모에선 방식 1로도 통과합니다. 하지만 가이드가 "그대로 쓸 수 있을까?"라고 물은 의도는 "구조를 바꾸지 않고 확장하는 법을 고민하라"이다
    - 방식 2는 "확장 지점을 어떻게 설계하는가"를 손끝으로 경험하게 됨. 그게 미션의 중심(트레이드오프를 자기 손끝으로)에 더 가깝다.

  **`인사이트 4`** -세션으로 시작한 결정이 여기서 "일거리"가 된다 (그게 의도다)

    - 앞서 세션으로 시작하기로 했다. 그 결정의 청구서가 바로 이 2단계이다.
    - 1단계(웹): 세션 → 쿠키 자동 → 매끄러움.
    - 2단계(모바일): **세션은 쿠키 기반인데 모바일은 쿠키가 어색하다.** 그래서 토큰 기반 추출기를 새로 만들어 [A]에 추가해야 한다.

    - 이건 "잘못 골랐다"가 아니라, **미션이 의도한 학습 지점**이다.
        - "웹에서 편한 방식이 모바일에서도 편한가? 인증 정보를 쿠키에 둘 것인가, 헤더에 둘 것인가?" 세션으로 시작했기에 이 질문을 **실제 코드 변경으로** 만나게 됨
        - 반대로 토큰으로 시작했다면 2단계는 "이미 헤더 기반이라 할 게 없네"가 됨 0 편하지만 배울 게 없다.
        - 세션으로 시작한 덕에 2단계가 "진짜 확장 작업"이 되고, 그 과정에서 방식 1 vs 방식 2(추상화) 같은 설계 결정을 만나며 곧 학습으로 이어진다.
    - 모바일 확장을 하다 보면 "그럼 웹도 그냥 토큰으로 통일하면 안 되나?" 라는 유혹이 온다.
        - 가능한 선택이고, 실제로 많은 서비스가 그렇게 한다. 하지만 그러면 미션 2단계의 "두 방식을 비교한다"는 학습 목표가 사라짐 - 비교하려면 둘 다 살아 있어야 함.
        - PR에 남길 만한 판단: "웹은 세션, 모바일은 토큰으로 공존시켰다. 통일할 수도 있었지만 두 방식의 트레이드오프를 직접 비교하려고 공존을 택했다."

  **`인사이트 5` - 확장하면 드러나는 숨은 차이들**

  [A]만 바꾸면 된다고 정리 했지만, 모바일을 실제로 붙이면 잔물결이 몇 개 일어남(미리 알아두면 당황하지 않음)

    - **로그인 응답이 갈라진다.**
        - 웹 로그인은 응답으로 `Set-Cookie`를 내려보냄.
        - 모바일 로그인은 응답 본문에 토큰을 담아 내려줘야 함(앱이 저장하게).
        - → `POST /login`의 응답 형태가 클라이언트에 따라 달라질지, 아니면 항상 토큰을 본문에 주고 웹은 쿠키도 같이 줄지  - 결정할 지점.
    - **"세션 없음"과 "헤더 없음"의 실패 메시지.**
        - 질문 3에서 인증 실패는 `UnauthorizedException` → 전역 핸들러로 `{message}` 형식이 된다고 했다. 모바일이 붙어도 이 인프라는 그대로 재사용됨
        - 추출기가 어느 방식으로도 사용자를 못 찾으면 똑같이 `UnauthorizedException`. 에러 응답은 일관되게 유지됨
    - **CSRF/CORS 같은 주제.**
        - 쿠키 기반과 헤더 기반은 보안 특성이 다름.
        - 다만 가이드가 "본격적인 보안 모델링은 제외 범위"라고 명시했으니, 이번 미션에선 "이런 차이가 있다"는 인식까지만하고 우선 깊게 안팜.


### 사전학습 제출물

내가 이해한 세션과 토큰의 가장 큰 차이는 로그인 상태(state)를 누가 들고 있느냐이다.
세션은 서버가 기억하고 클라이언트는 세션 ID만 들고 다니지만, 토큰은 클라이언트가 증표 자체를 들고 다니고 서버는 매 요청을 검증만 한다.

내가 가장 헷갈렸던 인증/인가 선택지는 **세션과 토큰 중 무엇을 출발점으로 선택할지**였다.
사전학습 코드 샘플이 세션 기반이고, 이번 미션이 **웹에서 시작해 모바일로 확장하는 흐름**으로 트레이드오프를 경험하도록 설계되어 있다고 느꼈다.
그래서 우선은 웹 환경에 자연스러운 **세션 방식으로 시작**하고, 2단계에서 모바일 확장을 고려하며 **헤더 기반 인증 방식을 덧대보는 방향**으로 정했다.

다만 여전히 궁금한 지점도 남아 있다.
만약 처음부터 토큰 방식을 선택했다면 2단계의 모바일 확장이 더 자연스러웠을지,
그리고 흔히 토큰을 “stateless하다”고 설명하지만 **동시 로그인 방지나 강제 로그아웃 같은 요구사항**을 만나면
결국 서버가 별도의 상태를 관리해야 하는 것은 아닌지 헷갈렸다.

즉, 이번 선택은 단순히 세션이냐 토큰이냐의 문제가 아니라,
**현재 요구사항에 맞는 출발점을 정하고 이후 확장 과정에서 각 방식의 트레이드오프를 직접 확인해보는 과정**이라고 생각했다.

**Interceptor와 ArgumentResolver의 차이**

Interceptor와 ArgumentResolver의 차이는 **Interceptor는 요청이 컨트롤러에 닿기 전에 "이 요청을 통과시킬지 막을지(로그인 했네, 통과)"를 결정하는 문지기이고, ArgumentResolver는 통과된 요청에서 현재 로그인 사용자를 꺼내 컨트롤러 파라미터에 채워주는(그 로그인한 사람은 브라운, 그 객체 줄게) 배달부라는 것** 이다. 즉 Interceptor는 요청의 통과 여부를, ArgumentResolver는 컨트롤러가 받을 값을 책임진다. 이 둘은 경쟁 관계가 아니라 분업 관계이다.

내가 이번 미션에서 인증 처리를 위해 먼저 써보고 싶은 도구는 **Interceptor** 이고, 이유는 **인증(로그인 여부 확인)은 요청을 컨트롤러에 들이기 전에 가장 먼저 막아야 하는 1차 방어선이라, 그 차단 지점을 먼저 세워두어야 ArgumentResolver가 "이미 인증된 요청"을 전제로 현재 사용자를 안전하게 꺼낼 수 있기 때문** 이다.

- 이 둘은 **경쟁 관계가 아니라 분업 관계.**
- "Interceptor와 ArgumentResolver의 차이는 **Interceptor는 요청을 막을지 통과시킬지 결정하고(로그인 했네, 통과), ArgumentResolver는 통과된 요청에서 현재 사용자를 컨트롤러 파라미터로 전달(그 로그인한 사람은 브라운, 그 객체 줄게)한다**
